# Ретайр off-store каналу дистрибуції — design (#267 Крок 2)

**Issue:** GH #267 (серія `chrome-web-store`), Крок 2. Попередній дизайн: `docs/superpowers/specs/2026-07/2026-07-10-cws-distribution-migration-design.md` (#247).
**Дата:** 2026-08-08
**Статус:** design → implementation

## Контекст

Перехід на Chrome Web Store завершено з боку публікації:

- Store-версія **0.13.0 схвалена й роздається** (CRX update endpoint віддає 0.13.0 для
  `fdelmnhijeiojadcaihfdpecfcldbndg`).
- Видимість листингу — **Public**, але розширення позначене **Mature Content** (алкогольна
  тематика), тож CWS ховає його від незалогінених і не показує в пошуку. Прямий лінк
  працює для будь-кого залогіненого — перевірено з іншого акаунта.
- Тестерів **четверо** (`SELECT DISTINCT telegram_id FROM api_tokens`): 3 з локаллю `uk`, 1 `en`.
- Через off-store канал востаннє реально доставлено **0.10.0**: у рядків 0.12.0 і 0.13.0
  `extension_releases.file_id IS NULL`, тобто розсилки не було.

Off-store канал (§6.1) далі не потрібен: CWS оновлює користувачів сам.

## Рішення (діалог з користувачем, 2026-08-08)

1. **Таблицю `extension_releases` лишаємо.** Перестаємо писати, але не дропаємо міграцією.
   Ретайр каналу — про код і UX, а не про дані; руйнівна міграція нічого не дає (кілобайти
   місця), а схема лишається на випадок відновлення каналу.
2. **`/extension` більше не надсилає zip** — віддає токен і посилання на стор.
3. **Ріжемо по шву «збірка ↔ публікація»** (уточнено користувачем 2026-08-08). Видаляється
   лише **публікація**; локальна збірка dev-варіанта лишається як інструмент мейнтейнера для
   дебажних версій «суто для себе». Шов чистий: `extension/scripts/zip-dist.py`
   самодостатній, а `zip-determinism.test.ts` згадує `extension_releases` лише в коментарі,
   без імпорту.
   **Лишається:** `build`, `package` (dev-zip), `build:store`, `package:store`,
   `zip-dist.py`, `key` у dev-маніфесті (пінить dev extension ID, тож токен переживає
   переустановку) і `zip-determinism.test.ts`.
   **Іде:** усе, що штовхає збірку в канал — включно з release-notes машинерією (див. нижче).
4. **Дебажний потік — `npm run build`, що вже віддає zip** (уточнено користувачем
   2026-08-08). Збірка йде на віддаленому сервері, тож потрібен **один архів для
   скачування**: `extension/warsaw-beer-overlay-<version>.zip`, який власник забирає з
   файлового дерева code-server. `dist/` як каталог для Load unpacked не годиться — він на
   сервері, а Chrome у власника локальний.
   **Скрипт `package` видаляється, а не спрощується.** У `extension/package.json` є хук
   `postbuild: python3 scripts/zip-dist.py`, тож `npm run build` уже робить zip; після
   виймання `release-notes.ts` скрипт `package` (`vite build && python3 scripts/zip-dist.py`)
   став би точним дублікатом `build`. Дві назви для однієї дії — саме те, що плутає.
   `package:store` лишається: `build:store` не тригерить `postbuild` (npm чіпляє хук лише до
   точної назви `build`), і його викликає `release:store`.
5. **Видаляємо, а не вимикаємо.** Мертвий шлях, який ніхто не викликає, гниє швидше, ніж
   його встигають знову перевірити.
6. **§6.1 розчиняється, а не видаляється.** Секція змішує канал дистрибуції з семантикою
   бейджів (`✅`/`⭐`/`❓`/`⚪`) і правилами збірки — бейджі чинні й лишаються.
   Перенумерації §6.2–6.4 **не робимо**: вона зламала б перехресні посилання по спеці й доксах.
7. **Мердж-гейт:** PR не мерджиться, поки всі четверо не підтвердять міграцію. Ретайр не
   ламає вже встановлені unpacked-копії, але забирає єдиний спосіб щось їм доставити,
   якщо хтось спіткнеться на віковій стіні або не має Google-акаунта.

## Обсяг

### Видалити

| Файл | Чому |
|---|---|
| `scripts/publish-extension-release.ts` (+ тест) | запис рядка релізу в БД бота |
| `deploy/bin/apply-extension-release.sh` + `scripts/apply-extension-release.test.ts` | привілейований applier для прод-БД (сам applier — shell-скрипт, `.ts`-сиблінга нема) |
| `src/bot/commands/extension-release.ts` (+ тест) | приймання zip від адміна + двокрокова розсилка |
| `src/storage/extension_releases.ts` (+ тест) | увесь доступ до таблиці стає непотрібним |
| `extension/package.json` → скрипт `release` | лише він склеює `package` з публікацією |
| i18n `extrel.*` та `extension.download` (uk/en/pl + `types.ts`) | рядки лише цього каналу |
| `extension/scripts/release-notes.ts` | пише `dist/RELEASE_NOTES.txt` — артефакт **лише** для каналу |
| `extension/src/shared/release-notes.ts` (+ тест) | `extractNotes` має єдиного споживача — файл вище |
| `extension/package.json` → `tsx scripts/release-notes.ts` зі скрипта `package` | наслідок двох рядків вище |

`listExtensionTokenHolders` живе в `extension_releases.ts`, але читає `api_tokens`; єдиний
її споживач — розсилка, тож вона йде разом з модулем.

### Явно НЕ чіпати (збірка лишається)

`extension/package.json` → `build`, `package`, `build:store`, `package:store`;
`extension/scripts/zip-dist.py`; `key` у dev-гілці `manifest.config.ts`;
`extension/src/build/zip-determinism.test.ts`.

**Дебажний потік після ретайру:** `npm run package` у `extension/` → один архів
`extension/warsaw-beer-overlay-<version>.zip` → власник качає його з файлового дерева
code-server, розпаковує локально, ставить через Load unpacked.

Скрипт `package` при цьому **спрощується** до `vite build && python3 scripts/zip-dist.py`.
Видалення `release-notes.ts` — не побічний збиток, а прибирання тертя: `extractNotes`
**падає**, якщо в `CHANGELOG.md` нема секції під поточну версію, тобто зараз дебажну
збірку неопублікованої версії зібрати не можна взагалі. Єдиним споживачем
`dist/RELEASE_NOTES.txt` був `publish-extension-release.ts`, який ми й видаляємо, тож
після ретайру файл нікому не потрібен. `package:store` цей крок і так не викликає —
store-шлях не зачеплено.

### Змінити

- `src/index.ts` — прибрати реєстрацію `extensionReleaseCommand`.
- `src/bot/commands/extension.ts` — прибрати `latestDeliverableRelease` і
  `replyWithDocument`; додати посилання на стор у повідомлення з токеном.
- `deploy/sudoers.d/warsaw-beer-bot` — **змін не потребує**: у репозиторній версії запису
  про `apply-extension-release.sh` нема. Але на **живому хості** `/etc/sudoers.d/` містить
  рядок `(warsaw-beer-bot) NOPASSWD: /usr/local/bin/apply-extension-release.sh` (видно в
  `sudo -l`) — тобто файли розійшлися ще раніше. Після ретайру цей рядок стає мертвим;
  прибрати його вручну (root-крок поза NOPASSWD-набором, за власником).

### Докси (user-facing зміна → той самий PR, правило CLAUDE.md)

- `docs/extension-install-uk.md`, `docs/extension-install-en.md` — встановлення **зі стору**
  замість «Load unpacked»; додати нотатку про «Item not available» → треба залогінитись
  (Mature Content), бо інакше це виглядає як битий лінк.
- `docs/extension-release.md` — прибрати рунбук off-store каналу (пересилання zip боту,
  двокрокова розсилка, applier); лишити `npm run release:store` як релізний шлях і додати
  короткий розділ про дебажну збірку (`npm run package` → скачати zip із сервера →
  розпакувати → Load unpacked локально).

### Спека

- **§6.1** — прибрати legacy-банер і бульєти каналу («бот zip не парсить», розсилка,
  оновлення розпакуванням поверх теки). Лишити бейджі; бульєт про збірку переписати:
  `release:store` для релізу + локальний `build`/`package` як дебажний інструмент
  мейнтейнера, без згадок про запис у `extension_releases` і стейджинг у
  `~/extension-releases/`. Секцію перейменувати відповідно до залишку.
- **§3.12 `extension_releases`** — позначити як retired: таблиця лишається, не пишеться.
- **§6.4** — стає єдиною секцією про дистрибуцію: модель CWS, store ID, наслідок зміни ID,
  **Mature Content** і його наслідки (невидимість для незалогінених + відсутність у пошуку),
  нова поведінка `/extension`. Чернетку міграційного повідомлення замінити на фактичний
  розісланий текст.

### Фактичний текст розсилки (замінює чернетку в §6.4)

Ключові відмінності від чернетки, обидві знайдені при підготовці:

1. **Основний шлях — перевикористати наявний токен** зі старого повідомлення в чаті, а не
   брати новий. Токен ні до якого extension ID не прив'язаний (`findTelegramIdByHash`), тож
   працює в обох копіях одночасно. `/extension` лишається запасним шляхом з явним
   попередженням: він робить деструктивну ротацію 1:1 (`DELETE` → `INSERT`, `api_tokens.ts`),
   тож одразу вимикає стару копію — тестер, який спіткнеться після цього кроку, лишиться
   взагалі без робочого розширення.
2. **Причина видалити стару копію** — не «вона непотрібна», а що дві копії малюють бейджі на
   тій самій сторінці й дублюють одна одну.

## Поза обсягом

- Дроп таблиці міграцією (рішення 1).
- Телеметрія міграції. Автоматичного сигналу не існує: `api_tokens.created_at` не зміниться
  при перевикористанні токена, `api_usage` тримає лише добові агрегати, а ні версія
  розширення, ні його ID у запитах `/match` не пишуться. Перед мерджем — просто спитати
  всіх чотирьох; заради чотирьох людей телеметрія не варта зміни протоколу.
- Чистка локальних `extension/warsaw-beer-overlay-*.zip` — вони gitignored, у git їх нема.

## Тестування

- Видалені модулі → видалені й тести; решта сюїту має лишитись зеленою (`npm test`, `tsc`).
- `src/bot/commands/extension.test.ts` — переписати під нову поведінку: токен + посилання на
  стор, **без** `replyWithDocument`.
- `src/storage/schema.test.ts` — таблиця лишається, тож тест схеми не змінюється; це і є
  перевірка рішення 1.
- `extension/src/build/zip-determinism.test.ts` — лишається зеленим без змін (імпортів з
  видаленого коду не має). Оновити в ньому лише застарілий коментар: детермінізм існував
  заради upsert-no-op по sha256 в `extension_releases`, і ця причина зникає — тест
  лишаємо як гарантію відтворюваності збірки.
- **Ключова регресія цієї зміни:** `npm run package` має відпрацювати для версії, якої
  **нема** в `CHANGELOG.md` — саме це раніше валило збірку і саме заради цього виймаємо
  `release-notes.ts`. Перевіряється тимчасовим бампом версії в `extension/package.json`
  без правки CHANGELOG.
- Ручна перевірка дебажного потоку: `npm run package` → скачати
  `extension/warsaw-beer-overlay-<v>.zip` → розпакувати → Load unpacked → бейджі
  малюються, токен зберігається (dev `key` на місці).
- `extension/src/shared/release-notes.test.ts` видаляється разом із модулем; переконатися,
  що `extractNotes` більше ніхто не імпортує.
- Перевірити, що `npm run release:store` (#266) не зачеплено — спільного коду з видаленим
  шляхом нема, лише згадка в коментарі `publish-store-release.ts`.

## Ризики

- **Мердж до міграції тестерів** — знімається мердж-гейтом (рішення 5).
- **Забути i18n-ключ** і зламати білд типів — `types.ts` типізує ключі, тож `tsc` спіймає.
- **Розсинхрон sudoers репо ↔ хост** — уже існує (див. вище) і ретайром не створюється.
  Мертвий рядок деплой не ламає, але лишає дозвіл на скрипт, якого більше нема; прибрати
  вручну при нагоді.
