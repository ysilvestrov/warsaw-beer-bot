# Фестивальні Target за назвою

## Проблема

Пиво, зварене спеціально під фестиваль, — перше, заради чого варто стояти в черзі: ніде більше
його не буде. Рейтингу в нього ще немає, тож у Target воно потрапляє лише тоді, коли пощастить зі
стилем або міцністю. Фест позначає таке пиво в назві («WFP 22», «WFP Speciality», «WFP 2026»).

## Виміри (прод-БД, меню WFP22, 2026-10-13)

600 позицій меню. «WFP» у назві (регістронезалежно) мають 11, жодного з них ніхто з команди не пив:

| Пиво | Стиль | ABV | Target зараз |
|---|---|---|---|
| Bro Hero: Mateusz WFP Speciality 1–3 | Historical Beer - Grodziskie | 3.0 | стиль (шаблон `Historical` з 12.10) |
| Sweet Temptation WFP Speciality 1–3 | Barleywine - Other | 12.0 | стиль, міцність |
| Stargazer WFP Speciality 1–3 | IPA - Belgian | 9.0 | міцність (поріг із 13.10) |
| Krasnolód Double Barrel … WFP 2026 | Freeze-Distilled Beer | 19.0 | стиль, міцність |
| Hyperjuice WFP 22 | Sour - Smoothie / Pastry | 5.5 | **ні** |

Хибних збігів серед 11 немає. Десять проходять завдяки налаштуванням, зробленим за останні дві
доби з інших причин; одинадцяте не проходить. Наступна фестивальна IPA чи лагер звичайної
міцності випаде так само.

### Чому окремий список, а не пошук шаблонів стилю в назві

Пошук чинних шаблонів стилю в назві відхилено у
`2026-10-13-fest-target-min-abv-design.md`: 2 збіги, обидва хибні («Wild Strawberry», «Tomato &
Basil»). Слова стилю в назві — смак, а не стиль. Позначка фесту — інше: вона стоїть лише в назві й
більше ніде. Тому списки окремі, і шаблон назви ніколи не шукається в стилі, а шаблон стилю — в
назві.

## Рішення

Четверте автоматичне правило: пиво, непите кожним учасником, стає Target, якщо його назва містить
хоч один із шаблонів фесту.

- `fests.target_name_patterns TEXT NOT NULL DEFAULT '[]'` — JSON-масив рядків, як
  `target_style_patterns`. Порожній масив — правила немає (поведінка як досі).
- Значення вписує оператор руками, а `toFest` розбирає його на кожному читанні фесту, тож зіпсований
  JSON клав би і команди фесту, і опитування (AI-рев'ю PR #865). Колонка несе
  `CHECK (json_valid(…) AND json_type(…) = 'array')`: хибний `UPDATE` падає одразу, в оператора на
  очах. Елемент масиву, що не є рядком, шаблоном не вважається й відкидається при читанні.
- `TargetCriteria.namePatterns: string[]`, `TargetMenuItem.name: string` (рядок меню вже його несе).
- Збіг — регістронезалежний підрядок у `beers.name`. Назва броварні, секція і стиль не
  переглядаються.
- Порожній шаблон (`''` або самі пробіли) ігнорується: підрядок `''` є в кожній назві, і один
  такий запис зробив би Target з усього непитого меню. Пробіли по краях шаблону обрізаються.
- Нова причина `'name'`; порядок причин: `rating`, `style`, `abv`, `name`, `manual`.
- `/fest targets` показує причину міткою `🎪 фестивальне` / `festiwalowe` / `festival special`
  (`fest.reason_name`).
- Список `unrated` означення не міняє, тож фестивальне пиво без рейтингу переходить із нього в
  Target. Ручні `add`/`remove` діють як досі.

### Міграція й значення

v49: `ALTER TABLE fests ADD COLUMN target_name_patterns TEXT NOT NULL DEFAULT '[]' CHECK (…);` — чистий
expand. Попередній реліз читає `fests` через `SELECT *` і зайве поле ігнорує; причини Target ніде
не зберігаються. Відкат лише коду безпечний.

Значення для `wfp22` виставляється операційно після деплою:
`UPDATE fests SET target_name_patterns = '["WFP"]' WHERE slug = 'wfp22'`. У міграцію `UPDATE` не
кладеться: це налаштування, а не схема.

## Заявка → доказ

Зміна не записує нових фактів: `target_name_patterns` — налаштування оператора, причини Target
обчислюються на кожен запит і не зберігаються. Правило спирається на `beers.name` — назву з
Untappd. Заявка «`WFP` у назві означає фестивальне пиво» перевірена на меню вище: 11 з 11.
Вона стосується одного фесту й одного шаблону; інший шаблон оператор перевіряє так само, перш ніж
вписати.
