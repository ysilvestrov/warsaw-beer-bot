# #697: доказове закриття orphan-triage issue

Дата: 2026-09-24. Статус: дизайн на погодження.

## Контекст і межа

Закриття `parser_bug`/`matcher_bug` issue або зняття `orphan-triage` нині запускає
`unlock-fixed-orphans` для **кожного** прив'язаного рядка. `adjudicate` зберігає
лише негативний `unrescued`-вердикт; позитивний `rescued` зникає разом із
тимчасовим файлом. Навіть `unrescued` зараз розмикається (хоч і без rearm),
а відсутність будь-якого вердикту дає безкоштовний rearm. Тому ручне закриття
issue може випустити невирішену сироту назад у роботу.

Мета: закриття #677 та наступних parser/matcher issues має бути операцією з
поштучним доказовим підсумком; помилка оператора або обхід команди через
GitHub UI не повинні розімкнути невирішений рядок. #697 не визначає
ідентичності восьми сиріт #677 і не змінює їх у проді.

## Чотири результати для рядка

| Результат | Стійкий доказ | Дія при закритті |
| --- | --- | --- |
| `rescued` фіксом | застосований позитивний реплей для **цього** issue й незмінного входу; зберігаємо також знайдений bid | один безкоштовний rearm і `unlocked_at`; далі звичайний крон установлює лінк або невдача повертає рядок у тріаж |
| відома ідентичність старої картки | застосований #696: точний alias і запис `legacy_card_repairs`; сирота видалена | немає рядка для unlock |
| ідентичність доказово не встановити | активний запис #695 у `legacy_orphan_dispositions` для цього рядка й ключа | лишається неактивним; ні unlock, ні rearm |
| `unrescued`, `inconclusive`, `already_marked` або без вердикту | рішення відсутнє | закриття заборонене; навіть після ручного закриття замок не знімається |

`unrescued_at` — лише відповідь «цей фікс не рятує», а не дозвіл на закриття.
`retired_at` без окремого доказового рішення також не є четвертим шляхом.
Для issue іншого класу наявна політика поза межами цього дизайну.

## Позитивний реплей як стійкий доказ

Розширити `VerdictFile` для нового `rescued` результатом `bid` і ABV входу:
реплей має назвати, **який** матч знайдено і з якими даними. Проба лишається
read-only, з канаркою до і після, і не пише ні лінк, ні backoff. Застосування
файлу зберігає позитивний маркер у `enrich_failures` (міграція v36):
`rescued_issue`, `rescued_at`, `rescued_bid`, а також знімок brewery/name/ABV,
lookup count/time і монотонного `rearm_count`. `rescued_at` — час застосування;
`probed_at` зберігається окремо для аудиту. Маркер належить конкретному рядку
й issue, не всій issue.

Той самий транзакційний preflight, що вже захищає `unrescued`, перевіряє для
`rescued`: рядок існує, ще orphan, не retired, належить issue, має ті самі
brewery/name/ABV і той самий стан lookup/rearm. Якщо щось змінилось, вердикт
пропускається з причиною, а не перетворюється на доказ. Нові позитивні файли
суворо вимагають числового bid та ABV-знімка; старі файли без цих полів не
можуть поставити позитивний маркер. `--force` обходить лише вікове вікно
файлу, не перевірку живого рядка. Повторне застосування того самого доказу
ідемпотентне; інший bid або issue вимагає нового реплею. Чинний
`unrescued_at` не може співіснувати з позитивним доказом: спочатку явний
rearm і новий реплей.

Позитивний маркер *чинний* тільки доки поточний рядок і issue точно
відповідають знімку. Перетріаж, зміна назви/ABV, новий lookup, явний rearm
або retirement роблять його непридатним для closeout та unlock без нового
реплею. Можна лишити історичні поля для аудиту, але жоден читач не має
приймати застарілий маркер як чинний. Рядок, що зматчився між реплеєм і
закриттям, сам зникає з `enrich_failures` і не потребує unlock.

## Команда закриття й фоновий запобіжник

Нова операторська команда `close-orphan-issue --issue N` за замовчуванням
робить dry-run: звіряє, що GitHub issue відкрита й має `orphan-triage`, читає
всі прив'язані `enrich_failures` (без `--limit`) і друкує по кожному `beer_id`
один із трьох станів: чинний `rescued` доказ, активний #695 для тієї самої
issue та старого ключа, або **блокер**.
Рядки, прибрані #696, вже відсутні; команда також друкує наявні журнали
ремонту для цієї issue, щоб оператор бачив повний підсумок когорти. Наявність
лише `retired_at`, `unrescued_at`, закритого чужого issue або просто `untappd_id`
без узгодженого поточного стану не є автоматичним дозволом. Dry-run завершується
ненульовим кодом, якщо є хоч один блокер або GitHub/БД недоступні.

`--close` повторно виконує ці перевірки безпосередньо перед GitHub PATCH,
відмовляє за наявності блокера й закриває лише issue, яка все ще відкрита та
має потрібну мітку. Знімати `orphan-triage` окремо не потрібно: сам факт
закриття виводить issue з відкритого набору. Нова GitHub-операція не є
автономною дією крона; її запускає оператор після перегляду dry-run. Якщо
між перевіркою й API-відповіддю з'явився новий рядок, команда повідомляє
про неповний closeout, але реальний захист належить фоновій джобі нижче.

`unlock-fixed-orphans` перестає трактувати закриття/зняття мітки як доказ.
Він розмикає і дає rearm **лише** рядку з чинним позитивним маркером для
його `issue_number`. Решта лишаються locked: без `unlocked_at` і без зміни
backoff. Відхилені рядки рахуються й явно потрапляють у лог/щоденний статус
із `beer_id` та issue, щоб ручне закриття не стало тихим зависанням. GitHub
API-помилка, неповна сторінка відкритих issues та збій БД лишаються
fail-closed. Повторний такт ідемпотентний; уже розімкнені рядки не чіпаємо.

Між SQLite та GitHub немає спільної транзакції: команда мінімізує вікно
перевірка→close, але тільки перевірка кожного рядка в unlock гарантує, що
ручне закриття або новий рядок після preflight не створить rearm без доказу.

## Операторський порядок і міграція

1. Задеплоїти v36 та guard до закриття будь-якої parser/matcher issue;
   міграція не ставить позитивних маркерів заднім числом.
2. Аудитувати на проді вже закриті issues, що досі мають locked-рядки:
   guard може лишити їх locked, і це треба назвати в статусі, не бекфілити
   доказ за фактом закриття.
3. Для кожного рядка майбутнього closeout: доведений старий товар ремонтувати
   #696, невідому ідентичність виводити #695, справді врятований фіксом
   реплеїти й застосувати `rescued`. `unrescued`/непевний рядок лишає issue
   відкритою або спершу переїжджає на відповідну під-issue по одному рядку
   без зміни `review_class`. Конфлікт bid/аліаса не розв'язується силовим
   closeout: розібрати його за правилами #696 або залишити рядок блокером;
   ранбук має назвати цю розвилку.
4. Запустити dry-run, перевірити перелік `beer_id`, тоді явно `--close`.
   Після закриття перевірити, що тільки `rescued` рядки розімкнулись,
   а неактивні, невирішені та нові рядки не отримали rearm.

Ранбук §4.1/§5 має містити саме цей порядок, команду та спосіб побачити
блокери. `spec.md` §3.13 і опис unlock/adjudicate треба оновити одночасно з
кодом: нинішні речення про безумовний unlock стануть неправдою.

## Перевірки

- Міграція без бекфілу, обмеження/цілісність нового маркера.
- Проба з двома справними канарками дає bid/ABV; аварійна канарка не дає
  застосовного файлу. Старий файл не може встановити `rescued`.
- Застосування позитивного вердикту: успіх, повтор, stale input, чужий issue,
  rearm без зміни lookup-полів, зміна ABV, matched/retired/missing.
- Closeout: змішана когорта, тільки #695/#696, нуль рядків, `unrescued`,
  `inconclusive`, `retired_at`, GitHub-стан/мітка, новий рядок перед `--close`.
- Unlock: чинний proof дає один rearm; відсутній/чужий/застарілий proof не
  змінює рядок; ручне закриття й зняття мітки не обходять guard; помилки
  GitHub/БД не розмикають частину когорти.
- Повний `npm test && npm run typecheck`, рев'ю гілки до периферійних змін.

## Не робимо в #697

Не вгадуємо особу восьми сиріт #677, не переписуємо ABV без прапорця #696,
не змінюємо правила пошуку чи класи тріажу, не закриваємо GitHub issues без
явного операторського `--close`,
не бекфілимо позитивні докази з історичного `unrescued_at`, `retired_at` або
самого факту закриття.
