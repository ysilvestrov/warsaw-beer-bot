# Дизайн — поступові результати `/match` для великих каталогів (#667)

**Issue:** #667. **Статус:** дизайн схвалено для планування.

## Проблема і доказ

`runOverlay` у `extension/src/content/index.ts` уже ставить uncached картки в стан
`working`, але викликає `sendMatch(rawMisses.map(...))` один раз. `handleMatch` у
`extension/src/background/index.ts` ділить цей запит на частини по 200, чекає кожну
послідовно і повертає один зібраний масив лише наприкінці. Тому фінальні бейджі,
cache-записи та enrichment першої частини чекають на всі наступні частини.

Порожній проміжний стан з issue більше не є актуальним: його прибрав #648, показуючи
`working` до `/match`. #667 зменшує іншу затримку — час від `working` до фінального
стану для перших карток.

## Рішення

Content script сам ділить `rawMisses` на послідовні частини максимум по 200 карток.
Для кожної частини він викликає наявний `sendMatch`, одразу малює її фінальні стани,
записує її результати одним `cache:set-many` і запускає enrichment тільки для її
кандидатів. Background отримує вже обмежений запит і робить один `POST /match`; його
внутрішнє chunking-накопичення прибирається.

Chrome runtime message contract лишається `match` → `match:ok|match:err`: не вводимо
потік повідомлень, correlation id або додаткові listener lifecycle-и.

## Порядок та помилки

- Частини йдуть послідовно, у порядку `rawMisses`; це не збільшує паралелізм до API.
- Відповідь коротша за свою частину позначає server failure лише для решти цієї
  частини, як і нинішній контракт.
- Помилка `sendMatch` позначає network failure лише для карток цієї частини; наступна
  частина все одно запускається. Одна тимчасова помилка не повинна забрати результати
  вже готової або ще не запитаної частини.
- Кожна успішна частина передає весь свій набір записів одним `cache:set-many`. Наявна
  serial queue у service worker гарантує, що popup Refresh або інша вкладка не очистить
  частину старої відповіді між її записами.
- Enrichment бачить лише успішні результати власної частини, після її cache write.

## Межі

- Не змінюються `/match` request/response schema, server matcher, eligibility або
  backoff enrichment.
- Не змінюється стан `working`, його copy чи badge taxonomy — це відповідальність #648.
- Не додаються нові залежності або канали повідомлень між content script і service worker.
- `extension/CHANGELOG.md` описує видиму зміну: великі каталоги починають показувати
  готові бейджі раніше, поки решта сторінки ще перевіряється.

## Заявка → доказ

| Записаний факт | Доказ |
|---|---|
| Картка успішної частини має фінальний match state | відповідь `/match` для цієї картки; позиція у відповіді збігається з позицією у відправленій частині |
| Cache містить повний набір успішної частини | один `cache:set-many` після її успішної відповіді, виконаний serial queue service worker |
| Сирота придатна до enrichment | наявний `canEnrich` застосований до server `MatchResult` і shop card, без нової клієнтської eligibility логіки |
| Помилка не є результатом match | rejected `sendMatch` або коротка відповідь; картка показує failure і не отримує cache/enrichment запис |

## Перевірки

- RED: 201 uncached картка викликає `sendMatch` двічі; перші 200 отримують фінальний
  бейдж до розв'язання другого Promise.
- RED: після rejection першої частини друга все одно викликається та малює результат;
  перша показує network failure.
- RED: background більше не об'єднує декілька частин, коли message уже містить максимум
  200 карток.
- Existing: cache write залишається batch-atomic для кожної отриманої частини, а
  enrichment отримує тільки results відповідної частини.
