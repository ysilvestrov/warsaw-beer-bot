# Дизайн — MCP-сервер над `/match` (паритет із розширенням для агентів)

**Дата:** 2026-09-10

## Мета

Дати власникам токена доступ до матчингу каталогу з їхнього агента (Claude Code, Codex CLI)
рівно з тією ж силою, що дає браузерне розширення: надіслати список пив і дізнатись, що з
цього вже випито й з якою оцінкою, а що є в нашому каталозі та з яким глобальним рейтингом.

Це **новий канал доступу до наявної логіки**, а не нова логіка. Матчинг, drunk-модель і
рейтинги не змінюються; змінюється те, як їх запитують і — головне — наскільки чесно
описано те, що ми віддаємо, бо споживач тепер переказує відповідь словами.

## Скоуп

**Входить:** один HTTP-роут `/mcp` у наявному Hono-застосунку бота, одна тула `match_beers`,
автентифікація наявним per-user Bearer-токеном, окремий облік трафіку, інструкція для
користувача.

**Не входить (свідомо):**

- **Інші тули** — крани, пошук по одному пиву, зріз чекінів. Усе це є в БД і все це спокусливо,
  але жодне не є тим, що робить розширення. Друга ітерація, коли буде видно, що агенти реально
  питають.
- **OAuth 2.1.** Claude Code (`--header "Authorization: Bearer …"`) і Codex CLI
  (`bearer_token_env_var`) приймають статичний заголовок — перевірено живими фетчами
  документації 2026-09-10. Custom connectors у claude.ai (веб/десктоп) поля для статичного
  заголовка не мають узагалі, лише OAuth Client ID/Secret; підтримка веб-застосунку означала б
  окремий authorization server (`/.well-known/oauth-authorization-server`, dynamic client
  registration, екран згоди, PKCE, ротація токенів) — сабсистем, більший за сам MCP. Окрема
  спека, якщо колись знадобиться.
- **Enrich і синхронізація чекінів.** Обидва потоки спираються на **сесію користувача в
  Untappd** у браузері; агент її не має й мати не може.
- **Анонімний доступ.** На відміну від `/match` (#245), MCP вимагає токен. Причина не безпекова:
  анонімна відповідь має `is_drunk: false` на кожній позиції, і агент перекаже це як «ти нічого
  з цього не пив». У розширенні ⚪ візуально відрізняється від ⭐; у переказаному тексті ця
  різниця зникає повністю.

## Транспорт

`@modelcontextprotocol/sdk@1.30.0`, модуль `server/webStandardStreamableHttp` —
транспорт на Fetch API. У його власному докблоці стоїть приклад для Hono:
`app.all('/mcp', async (c) => transport.handleRequest(c.req.raw))`.

Два параметри, і жоден із них не є смаком:

- **`sessionIdGenerator: undefined` (stateless).** Сесія stateful-режиму живе **в пам'яті
  процесу**. Процес бота перезапускається на кожному деплої, а сесія клієнта — ні: після
  деплою клієнт із живою сесією дістав би `404 Not Found` на кожен наступний запит замість
  прозорого переконнекту. Свіжий `McpServer` + транспорт на кожен запит — нуль стану, нуль
  цієї категорії.
- **`enableJsonResponse: true`.** Прибирає довгоживий SSE-стрім. Наш ендпоінт стріму не
  потребує (одна тула, один синхронний результат), а довгоживі з'єднання через cloudflared у
  цьому проєкті вже коштували інциденту: гонка keep-alive між Node і тунелем давала
  Cloudflare 502 (#124), через що в `src/api/index.ts` і стоять `keepAliveTimeout = 120s` /
  `headersTimeout = 125s`. Не заводити другий довгоживий шлях — дешевше, ніж захищати його.

Ціна SDK — **88 пакетів / 29 MB** у прод-дереві (виміряно `npm i` в чистій теці; поточне
прод-дерево — 87 записів, тобто залежність його подвоює). Важкі піддерева (express, jose, ajv,
pkce-challenge, eventsource) приходять із модулів auth/express, яких ми не імпортуємо: вони
ніколи не `require`'ляться, тож це вага на диску, не в рантаймі. Алерти на них обробляє
наявний конвеєр #435. Альтернатива — свій JSON-RPC на ~150 рядків (`initialize`,
`notifications/initialized`, `tools/list`, `tools/call`, `ping`) без нових залежностей —
відкинута: вона економить диск і платить відповідальністю за чужу специфікацію, а баг
сумісності виглядав би як «у Codex не працює», без сліду в наших логах.

## Архітектура

```
src/api/routes/mcp.ts       app.all('/mcp'), транспорт, connect, handleRequest
src/api/mcp/server.ts       збирання McpServer + реєстрація тули; про HTTP не знає
src/api/mcp/match-tool.ts   контракт тули: вхід → matchBeerList → статуси
```

Авторизація — наявний `authMiddleware(deps.db)`, той самий, що на `/enrich/*`: sha256 →
`api_tokens` → `telegram_id`, інакше `401 {"error":"unauthorized"}`. Нового коду в
автентифікації нема. Ліміт тіла — наявний `payloadBodyLimit` з `MATCH_BODY_LIMIT_BYTES`
(256 KiB), доданий для `/mcp` у `createApiApp`.

CORS лишається `origin: '*'`: сторінка в браузері токена не має, тож її зупиняє 401.
DNS-rebinding-захист SDK (`allowedHosts`) призначений для локальних серверів; наш стоїть за
тунелем із публічним іменем.

**Рефактор, обов'язковий для коректності.** `createCatalogCache` зараз створюється
**всередині** `matchRoute` (`src/api/routes/match.ts:34`). Якщо MCP створить власний, у процесі
житимуть два незалежні кеші підготовленого каталогу на ~30k пив — подвійна пам'ять і подвійна
перезбірка на кожен бамп `catalog-version`. Кеш підіймається в `createApiApp` і передається
обом роутам як спільний інстанс.

## Контракт тули

`match_beers`. Вхід (zod → JSON Schema генерує SDK):

```
beers: [{ brewery: string, name: string, abv?: number }]   // 1..200
```

Обидва текстові поля обов'язкові. Розділення пивоварні й назви робить сама модель — вона це
вміє краще за будь-яку евристику, яку ми написали б, а порожня пивоварня має конкретну ціну:
вона веде айтем у повнокаталожний fallback, бюджетований 20-ма на запит (`FULL_FALLBACK_BUDGET`,
`src/domain/matcher.ts:24`). Exact-шлях порожню пивоварню переживає (split-invariant друга
спроба, #169), fuzzy — ні.

Вихід — `structuredContent` плюс компактний текстовий рендер. На кожну позицію:

| Поле | Значення |
|------|----------|
| `input` | `{brewery, name}` як надіслано (щоб модель могла зіставити рядки) |
| `status` | `drunk` \| `probably_drunk` \| `not_drunk` \| `not_in_catalog` \| `not_searched` |
| `confidence` | `exact` \| `fuzzy` — лише коли є `beer` |
| `beer` | `{name, brewery, rating_global, untappd_url}` або `null` |
| `your_rating` | число або `null` (лише для `exact`) |

Плюс блок `profile` на всю відповідь (див. «Порожній профіль» нижче).

### Три заявки, які тонкий проксі зробив би хибними

**(а) `confidence`.** У сьогоднішній відповіді `/match` пиво, зматчене **fuzzy** і **не**
випите, невідрізниме від exact-збігу: `matched_beer` заповнене, `is_drunk: false`,
`drunk_uncertain: false`, `user_rating: null`. Розширення це переживає, бо обидва дають ⚪.
Модель — ні: вона скаже «Atak Chmielu, 3.9, ти його не пив», хоча ми не впевнені, що це те саме
пиво. Тому `MatchListResult` дістає поле `source` (`'exact' | 'fuzzy'`), яке вже є всередині
`matchPrepared`, але не виходить назовні. Поле адитивне й з'явиться також у відповіді `/match`
(розширення ігнорує незнані поля) — отже, рядок у `spec.md`.

**(б) `not_searched`.** Бюджет повнокаталожного fallback — 20 **на запит**. Двадцять перша
позиція з невідомою нам пивоварнею повертає `matched_beer: null`, не будучи шуканою, і сьогодні
це невідрізнимо від «шукали й не знайшли». Агент перекаже перше як друге. `matchBeerList` має
лише агрегат `budget.budgetSkipped`; робимо його по-позиційним **локально**: звіряємо
`budgetSkipped` до й після кожного айтема і, якщо він зріс, позначаємо позицію. `matcher.ts` не
змінюється взагалі.

**(в) Порожній профіль.** Найтихіша з трьох. Drunk-set — це `checkins ∪ untappd_had` (§5.2,
`triedBeerIds`), а обидва наповнює **розширення**: enrich-потік і синхронізація чекінів, плюс
`/import`. Користувач, який поставив MCP і ніколи не користувався розширенням, має **порожній**
drunk-set — і дістане впевнене `not_drunk` на кожну позицію. Формально це не брехня (у нас
справді нема запису), але переказане моделлю воно стає твердженням про людину, а не про нашу
БД.

Тому: відповідь несе блок `profile` — `{checkins_known, untappd_had_known, last_checkin_sync}` —
і, **коли drunk-set порожній**, статус `not_drunk` по всій відповіді замінюється на `unknown`.
Одна умова на виклик, не на позицію. Каталожна частина (`beer`, `rating_global`, `confidence`)
при цьому працює як завжди: ми не знаємо, що людина пила, але добре знаємо, що це за пиво.

## Таблиця «заявка → доказ»

| Заявка | Що стверджує | Доказ |
|--------|--------------|-------|
| `status: drunk` + `your_rating` | людина пила саме це пиво | `source === 'exact'` І `beer.id ∈ triedBeerIds(telegram_id)`; оцінка — з `latestRatingsByBeer`. Exact = рівність нормалізованих назв або перетин `nameKeys` — той самий гейт, що вже несе ⭐ у розширенні |
| `status: probably_drunk` | ймовірно пила | `source === 'fuzzy'` І в drunk-set. Заявка **навмисно слабша** за попередню й названа так у самому значенні |
| `status: not_drunk` | у нас нема запису, що пила | drunk-set **непорожній** (інакше статус `unknown`) І `beer.id ∉` drunk-set |
| `status: not_in_catalog` | ми шукали й не знайшли | позиція **не** інкрементувала `budget.budgetSkipped`, тобто пошук реально відбувся |
| `status: not_searched` | ми не шукали | `budgetSkipped` зріс на цій позиції |
| `confidence: exact` \| `fuzzy` | наскільки певний збіг | `MatchResult.source` із `matchPrepared`, проведений назовні (нове поле) |
| `beer.untappd_url` | посилання на це ж пиво в Untappd | `beers.untappd_id` (не `match_links.untappd_beer_id` — той локальний `beers.id`, §5.2) |
| `profile.*` | обсяг того, що ми про людину знаємо | прямі `COUNT` по `checkins` / `untappd_had` + `checkin_sync_state`; це і є те, чим `not_drunk` доводиться |
| `api_usage.mcp_requests` / `mcp_beers` | трафік MCP за добу | інкремент у роуті на кожен прийнятий виклик. **Слабке місце, успадковане:** запис best-effort із `busy_timeout = 0`, тож під конкурентним записом лічильник мовчки губить одиницю. Це вже так для розширення (`api_usage.ts`), і ми свідомо не робимо MCP суворішим — лічильник лишається індикатором адопції, а не бухгалтерією |
| `anon_requests` / `authed_requests` | трафік **розширення** | MCP до них не торкається; тест це доводить прямо |

**Заявка, якої ми не робимо:** свіжість каталогу. `/match` матчить по кешу зі
stale-while-revalidate (#277): щойно записане пиво може з'явитися з затримкою ~2 с. Тула
успадковує це без змін і нічого про свіжість не стверджує.

## Облік

Міграція 30: `api_usage.mcp_requests`, `api_usage.mcp_beers` — обидві
`ALTER TABLE ADD COLUMN … NOT NULL DEFAULT 0`, без перебудови таблиці.

`recordMatchUsage` дістає аргумент `channel: 'extension' | 'mcp'`. MCP інкрементує **лише** нові
колонки. Причина: §3.16 оголошує `anon_requests`/`authed_requests` трафіком розширення, і
дайджест друкує з них рядок «Розширення /match (вчора)». Якби MCP пішов у ті самі лічильники,
рядок і далі стверджував би факт про розширення, рахуючи розширення плюс агентів, — і виявити це
було б нізвідки, бо число просто виросло б. Історичні значення теж не змінюють сенсу заднім
числом.

Дайджест (`src/jobs/daily-status.ts:37`, дані з `src/storage/stats.ts:106`) дістає окремий рядок
одразу під наявним: `• MCP /match (вчора): N запитів · M пив`. Нулі показуються так само, як у
рядку розширення. Анонімного розрізнення нема — MCP завжди автентифікований.

Лог на виклик — та сама форма, що вже пише `matchRoute` (`items`, `fullFallback`), плюс
`channel: 'mcp'` і `telegramId`.

## Помилки

Токен відсутній або невалідний → 401 наявного `authMiddleware`.

**Відкрите питання, яке вирішує проба, а не цей документ.** За MCP-специфікацією сервер має
віддавати на 401 заголовок `WWW-Authenticate` з посиланням на метадані ресурсу. Клієнт, який
його не бачить, може прочитати голий 401 як «сервер хоче OAuth» і піти шукати
`/.well-known/oauth-authorization-server` — і тоді користувач, який просто забув токен, побачить
помилку про OAuth. Це заявка про поведінку **чужого** клієнта, і перевіряється вона лише живим
підключенням. План містить окрему задачу: підключити реальний Claude Code і реальний Codex до
живого ендпоінта без заголовка й **подивитися**. Формулювання відповіді (голий 401 чи 401 з
`WWW-Authenticate`) визначається результатом проби.

Порожній результат матчингу помилкою протоколу не є — це нормальна відповідь зі статусами вище.
`isError` лишається для справжніх збоїв (перезбірка кешу каталогу впала); SDK ловить кинуту
помилку в хендлері `tools/call` і повертає її як **звичайний JSON-RPC `result` з HTTP 200,
усередині якого `isError: true`** — верхньорівневого JSON-RPC `error` при цьому не буває
(єдиний виняток у SDK — `McpError` з кодом `UrlElicitationRequired`, який перекидається як
помилка протоколу; ми таких не кидаємо). Це з'ясовано читанням коду SDK
(`server/mcp.js`: `catch` → `createToolError`) і закріплено тестом
`src/api/routes/mcp.test.ts` ще в стадії ядра — початкове формулювання цього абзацу
(«→ JSON-RPC error») було хибним.
Перевищення 256 KiB ловить наявний `payloadBodyLimit` і віддає HTTP-413 `{"error":
"payload_too_large"}` не в JSON-RPC-формі; клієнт покаже це як HTTP-помилку, що чесно.

## Тестування

- `src/api/mcp/match-tool.test.ts` — логіка тули на засіяній in-memory БД: exact + випите →
  `drunk` з оцінкою; fuzzy + випите → `probably_drunk`; **fuzzy і не випите → `not_drunk` з
  `confidence: fuzzy`** (випадок, заради якого існує поле); вичерпаний бюджет → `not_searched`;
  шукали й не знайшли → `not_in_catalog`; **порожній drunk-set → `unknown` замість `not_drunk`,
  при збережених даних каталогу**. Сиди з видимими значеннями (не `null`-дефолтами), кожен тест
  мутаційно доведений: прибери рядок реалізації — тест має впасти.
- `src/api/routes/mcp.test.ts` — крізь `app.request()`: повний цикл `initialize` → `tools/list` →
  `tools/call`; 401 без токена; 401 з чужим токеном; 413 понад ліміт.
- `src/storage/api_usage.test.ts` — MCP-виклик інкрементує `mcp_*` і **не чіпає**
  `anon_requests`/`authed_requests`.
- Тест на новий рядок дайджесту.
- Тест на спільність кеша каталогу: `createApiApp` не створює двох інстансів.

Повний гейт (`npm test && npm run typecheck`) на кожній задачі плану, не звужений.

## Стадії плану

План не пишеться цілком наперед (правило про стадії, CLAUDE.md). Спека одна на всю зміну, а
план ділиться надвоє:

**Ядро** — те, заради чого все робиться, і те, чого ще не існує: спільний кеш каталогу,
поля `source` й позиційний `searched` у `match-list.ts`, тула, роут, автентифікація. Далі —
наскрізне рев'ю ядра **разом із живою пробою 401** на реальних клієнтах.

**Обв'язка** — план пишеться **після** рев'ю ядра, проти коду, який уже існує: міграція 30,
`channel` в обліку, рядок дайджесту, `docs/mcp-uk.md`, `pages.yml`, рядок у `/extension`,
`spec.md`.

## Ризики

- **Вага залежності.** 88 пакетів у прод-дереві. Пом'якшення — конвеєр #435; але це реальна
  разова ціна, і саме вона робила підхід «свій JSON-RPC» не безглуздим.
- **Поведінка клієнтів на 401** — відкрита, вирішується пробою (вище).
- **Навантаження.** Агент може викликати тулу в циклі, а `/match` рейт-ліміту не має взагалі
  (§«Ліміти розміру запитів» лишає rate-limit як окремий follow-up). Захист поки що —
  200 позицій на виклик, 256 KiB на тіло і бюджет fallback. Новий лічильник `mcp_requests` існує
  зокрема для того, щоб побачити, чи це стало проблемою, **перш ніж** будувати рейт-ліміт.
