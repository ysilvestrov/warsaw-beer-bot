# #697: неактивне рішення після негативного реплею

Дата: 2026-09-24. Статус: дизайн на погодження.

## Дефект і межа

У production рядок 29893 issue #677 має активне рішення #695 для точної старої картки та попередній `unrescued_at`. `close-orphan-issue --issue 677` називає його блокером. Причина: `inspectOrphanIssue` вимагає `unrescued_at IS NULL` навіть для активного неактивного рішення. Тест, доданий комітом `a1c85c7`, закріпив цю умову.

Це суперечить `spec.md` §3.6.3: #695 навмисно не стирає `unrescued_at`. Водночас `spec.md` §5 та дизайн #697 визнають активне #695 рішення окремим close-out станом. Негативний реплей сам по собі не є таким рішенням.

Мета — дозволити close-out рядка з чинним точним #695 рішенням незалежно від попереднього `unrescued_at`, залишивши всі інші запобіжники. Зміна стосується лише класифікації в close-out gate; не змінює схему, дані, #695, #696, positive proof, unlock чи GitHub-операцію.

## Рішення

`inspectOrphanIssue` класифікує рядок як `inactive`, якщо є активний #695 запис для цього `beer_id`, того самого issue та точного поточного ключа `cardText(brewery)`, `cardText(name)`, `cardAbv(abv)`; пиво досі не має bid, а failure не `retired`. `unrescued_at` не входить до цієї перевірки. Класифікація `rescued` далі використовує чинний позитивний proof, а негативний маркер без #695 чи proof лишається `blocked`.

Не змінювати `unrescued_at` під час disposition або перед close-out: це історичний результат реплею, а не конфлікт з рішенням про невстановлену ідентичність. Не змінювати порядок інших перевірок чи текст блокерів. Закриття issue лишається явною операторською дією після dry-run і повторного preflight.

## Записи, які система приймає за факт

| Запис / читач | Що стверджує | Доказ і перевірка |
| --- | --- | --- |
| `legacy_orphan_dispositions` з `reopened_at IS NULL` | Оператор вирішив, що саме цей старий ключ не можна доказово прив'язати до bid | Поодиноке застосування #695 з причиною, evidence URL та оператором; close-out звіряє `beer_id`, issue, точний ключ, unmatched і not-retired стан |
| `enrich_failures.unrescued_at` | Негативний реплей не знайшов пиво на той момент | Застосований вердикт реплею; сам по собі не доводить ні невідомої ідентичності, ні готовності до закриття |
| `enrich_failures.rescued_*` | Позитивний реплей довів bid для незміненого рядка | Чинний proof за правилами #697; його перевірка не змінюється |
| Звіт `close-orphan-issue.ready` | Для кожного живого рядка є допустимий close-out стан | Повний перелік `enrich_failures` issue; кожен рядок `inactive` або `rescued`, без блокерів, плюс відкритий GitHub issue з `orphan-triage` |

## Перевірка і rollout

Тест має відтворити послідовність production: `unrescued_at` уже є, потім оператор ставить точне #695 рішення; звіт показує `inactive` і `ready: true`, а маркер у БД лишається. Контрольний рядок з одним лише `unrescued_at` лишається `blocked`. Наявні тести на чужий issue, змінений ключ, `retired_at`, matched beer та positive proof лишаються зеленими; окремий тест команди доводить, що без рішення `--close` не викликає GitHub PATCH.

Після PR, merge й deploy повторити `close-orphan-issue --issue 677` на production. Якщо він перелічує сім ремонтів #696 та 29893 як `inactive` без блокерів, запустити `--close`; перевірити закриту GitHub issue, чинність #695 запису, відсутність `unlocked_at`/rearm для 29893. До deploy не обходити gate ручним закриттям або скиданням `unrescued_at`.
