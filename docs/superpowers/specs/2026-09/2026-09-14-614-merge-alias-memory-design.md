# Дизайн — пам'ять злиття для назв з крамниць: `/match` впізнає картку після першого пошуку (закриває #614)

**Дата:** 2026-09-14 (двічі переглянуто того ж дня після наскрізних рев'ю ядра — див. «Рев'ю ядра»)
**Issue:** [#614](https://github.com/ysilvestrov/warsaw-beer-bot/issues/614). Бід-резолв → злиття → `/match` знову
`null`: ті самі пива шукаються в сесії Untappd на кожному завантаженні, а бейдж після пошуку не
показує статусу «пив».
**Пов'язані:**
- #366 — пам'ять злиття для кранів, `match_links.merged_at`;
- #384 — ідентичність за опублікованим bid;
- #617 — `numericNameTokens`, числові токени, які нормалізація назви відкидає;
- #632 — петля злиттів на шляху кранів, виділено;
- #633 — `/match` приймає опублікований bid, виділено;
- #618 — назва Untappd окремо від ключа матчингу.

## Проблема (доведена)

### Петля

Назва картки в крамниці часто не збігається з назвою рядка в каталозі. Тоді на **кожне**
завантаження сторінки:

1. `POST /match` повертає `matched_beer: null`, і картка стає сиротою.
2. `/enrich/candidates` → `ensureBeerRow` створює **новий** рядок-сироту з парою картки
   (`untappd_lookup_count = 0`, тобто `eligible: true`).
3. Розширення шукає пиво в сесії Untappd користувача. Далі `/enrich/result`: bid крамниці
   приймається (`resolveByBid`) або його знаходить пошук. Bid уже належить іншому рядку, тож
   спрацьовує `SQLITE_CONSTRAINT_UNIQUE` → `mergeIntoCanonical` → сироту **видалено**.
4. Клієнт малює ⭐ (`setEnriched`) і нічого не кешує. Сервер теж нічого не запам'ятовує для
   `/match`: `merged_at` (#366) живе лише на `match_links`, а їх читає тільки інжест кранів.

Після кроку 4 стан такий самий, як до кроку 1. Бекоф петлю не зупиняє, бо щоразу рахує
новий рядок.

### Статус «пив» губиться

Відповідь `/enrich/result` — це `{status, untappd_id, rating_global}`. `setEnriched` малює ⭐
лише з цих полів. Навіть коли пошук правильно знаходить випите пиво, бейдж не показує ні ✅,
ні особистої оцінки. Такі поля за побудовою є лише у відповіді `/match`.

## Рішення

Злиття запам'ятовує **текст картки, який перевірив пошук**, як **аліас** канонічного рядка.
`/match` і MCP перевіряють аліас **перед** матчером: ключ картки — нормалізована броварня,
нормалізована назва **і числові токени назви** — має точно дорівнювати ключу аліасу. Влучання дає
точний збіг з особистим статусом. Пошук, створення рядка й злиття більше не повторюються. Зміна
лише серверна: розширення не змінюється, ефект настає після деплою.

**Рівень доказу — ✅ для обох шляхів злиття** (рішення користувача, 2026-09-14).
- **Злиття за опублікованим bid:** магазин опублікував bid, гейт броварні його прийняв. Це
  сильніше за збіг назв.
- **Злиття з пошуку:** якби bid не належав уже іншому рядку, сирота з цією самою парою просто
  отримала б `untappd_id`, і `/match` сьогодні читав би її як `exact`.

Злиття не повинно робити відповідь слабшою, ніж без нього. І не повинно робити її **сильнішою**
для картки, про яку злиття нічого не доводило. Звідси три правила:
- ключ аліасу не втрачає цифр;
- текст аліасу — той, який шукали, а не текст рядка-сироти, що міг прийти від іншої картки;
- аліас доводить лише той bid, під яким його записано.

### Поза скоупом

- **#632** — петля злиттів на шляху кранів. Спільний `ontap_ref` скидає `merged_at`, механізм
  інший. Цей дизайн не змінює `refresh-ontap` і `ensureOrphan`.
- **#633** — bid у `/match`: точний бейдж без жодного пошуку. Потрібен реліз розширення.
- **#618** — назва Untappd як аліас. Таблиця з цього дизайну може прийняти й таке джерело,
  але тут його немає (YAGNI).
- **Суфікс `IS` у назвах Flasker.** Фікс парсера закрив би лише такі картки. Red Mexican
  ламається без жодного суфікса.

## Дані: таблиця `beer_aliases` (міграція v32)

```sql
CREATE TABLE beer_aliases (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  beer_id            INTEGER NOT NULL REFERENCES beers(id) ON DELETE CASCADE,
  brewery            TEXT NOT NULL,   -- як надіслала картка (сирий текст)
  name               TEXT NOT NULL,
  normalized_brewery TEXT NOT NULL,
  normalized_name    TEXT NOT NULL,
  name_digits        TEXT NOT NULL,   -- nameDigits(name): відсортовані числові токени через пробіл
  created_at         TEXT NOT NULL,
  UNIQUE (normalized_brewery, normalized_name, name_digits)
);
CREATE INDEX idx_beer_aliases_beer ON beer_aliases(beer_id);
```

- **Ключ** — `(normalized_brewery, normalized_name, name_digits)`. `normalizeBrewery`/`normalizeName`
  — ті самі, якими `ensureBeerRow` рахує пару з сирого тексту картки; `/match` отримує від
  розширення рівно той самий текст (`extension/src/content/index.ts`, `enrich.ts`).
- **`name_digits`** = `nameDigits(name)` = `numericNameTokens(name)`, відсортовані й склеєні
  пробілом. Це рівно те, що `normalizeName` відкидає, тож ключ втрачає не більше, ніж
  специфікацію і стиль. «Rochefort 8» і «Rochefort 10» — різні ключі; «Mjød» і «Mjød 2023» — теж.
- **Сирі `brewery`/`name`** — для аудиту й рецепта скасування.
- **Міграція v32 ще не застосована ніде**, тож колонка й унікальність змінюються в самій v32.
- **Бекфілу немає.** Сирота видаляється при злитті, тож відновлювати пару нема з чого. Таблиця
  заповнюється сама, щойно сторінку завантажать наступного разу (так само, як `merged_at`, #366).

## Запис

### `mergeIntoCanonical(db, orphanId, canonicalId, at, aliasSource?)`

У тій самій транзакції, **до** `DELETE FROM beers`:

1. **Текст аліасу** — `aliasSource` (броварня й назва, які шукав виклик), а без нього — сирі
   `brewery`/`name` рядка-сироти.
   - `applyLookupOutcome` передає свій `input` завжди. На шляху `/enrich/result` це текст
     запиту картки; на шляху крону — текст самої сироти, тож там поведінка не змінюється.
   - Причина: `ensureBeerRow` шукає рядок через `findBeerByNormalized`, а той не бачить цифр.
     Картка «Ґвара #7» дістає сироту, яку раніше створила картка «Ґвара #6», і пошук для «#7»
     зливає її. Текст сироти («#6») записав би аліас «#6 = рядок #7» — хибний ✅ (рев'ю 2,
     проба C).
2. **Ключ** рахується з тексту аліасу: `normalizeBrewery`, `normalizeName`, `nameDigits`.
3. **Аліас не пишеться**, якщо **інший рядок `beers`** (крім сироти) має ту саму нормалізовану
   пару **і** ті самі `nameDigits(name)`. Такий рядок сам є відповіддю для цієї картки.
   Близнюк з іншими цифрами запис **не** блокує: ключ аліасу від нього відрізняється.
4. **Запис:** `INSERT … ON CONFLICT(normalized_brewery, normalized_name, name_digits) DO UPDATE SET
   beer_id, brewery, name, created_at`. Той самий ключ, що вже вказував на інший рядок,
   переходить на новий: найсвіжіше злиття має найсвіжіший доказ.
5. **Аліаси рядка, що зливається, не переносяться** — їх забирає `ON DELETE CASCADE`.
   - Серверний крон (`enrichOneOrphan`) і пошуковий шлях `/enrich/result` збагачують лише
     сироти, а сирота аліасів не має. Рядок з аліасами (злінкований) потрапляє в злиття **лише**
     через репарацію #384: крамниця опублікувала bid, що суперечить його `untappd_id`.
   - Аліаси доводили **старий** bid цього рядка.

`mergeIntoCanonical` уже бампає версію каталогу, тож окремий бамп не потрібен.

### Зміна `untappd_id` рядка відкидає його аліаси

Аліас доводить «ключ = пиво з bid X». Коли в рядка змінюється bid, аліаси втрачають доказ.
Такий запис є рівно в двох місцях:

- **`recordLookupSuccess`** — репарація #384 переписує bid злінкованого рядка на новий (власника
  в нового bid ще немає). У транзакції з `UPDATE` видаляються аліаси цього рядка, якщо його
  `untappd_id` відрізняється від нового (`dropAliasesOnRelink`). Сирота й той самий bid — без змін.
  Якщо `UPDATE` падає на `UNIQUE`, транзакція відкочується, рядок далі зливається, і аліаси
  забирає каскад.
- **`pinMatch`, гілка «новий bid»** — людина пінить рядок на інший bid. Те саме правило.

`upsertBeerByBid` резолвить лише сироти, тож туди правило не потрібне.

## Читання: аліас перед матчером

### Завантаження (`loadAliases`)

- **Жива перевірка лінку.** Аліас на рядок без `untappd_id` не читається — та сама перевірка,
  що й `isRememberedMerge` (#366).
- **Рядок каталогу важить більше за аліас.** Аліас не читається, якщо інший рядок `beers` має
  ту саму нормалізовану пару **і** ті самі `nameDigits(name)` (пізніша сирота кранів; сирота, яку
  репарація #384 зробила рядком нового bid). Картку тоді відповідає матчер.
- SQL не рахує числові токени, тож запит повертає аліаси разом з назвами рядків тієї самої пари
  (`LEFT JOIN` по `idx_beers_norm`), а порівняння цифр робить TypeScript. Близнюк з іншими
  цифрами аліас не вимикає.

### Індекс у кеші каталогу

`createCatalogCache` поруч із `prepared` і `byId` будує `aliases: AliasIndex` — мапу «ключ →
`beerId`». Каталог матчера (`prepared`) аліасів **не містить**: матчер не бачить дублікатів `id`,
пул неточного пошуку для броварні не звужується, `byId` лишається з рядків `beers`.

`/match` і MCP (`match-tool.ts`) ділять один `CatalogCache` з композиційного кореня; обидва
передають `aliases` у `matchBeerList`.

### `matchBeerList`

Для кожної картки, **до** `matchPrepared`:

1. ключ = `normalizeBrewery(brewery)` | `normalizeName(name)` | `nameDigits(name)`;
2. в індексі є аліас з цим ключем **і** `byId` має його `beerId` → результат `exact` на цей рядок:
   `is_drunk`, `user_rating`, `searched: true`; матчер і бюджет повнокаталожного фолбеку не
   чіпаються;
3. інакше — матчер, як сьогодні.

**Цифри — частина ключа, рівність точна.**
- `ROCH / Trappistes Rochefort 10` проти аліасу `… Rochefort 8` → інший ключ → матчер.
- `ROCH / Trappistes Rochefort 10` проти аліасу `… Rochefort` (без цифр) → інший ключ → матчер.
- `VARVAR / MJØD IS 2023` проти аліасу `VARVAR / MJØD IS` на вінтаж 2021 → інший ключ → матчер.
- `X / Mjød` проти аліасу `X / Mjød 2021` → інший ключ → матчер. Така картка й далі проходить
  петлю: це свідома ціна безпечного боку.

## `/enrich/*` (периферія)

### `ensureBeerRow`

Порядок: рядок `beers` з парою **і сумісними цифрами** → **аліас з тим самим ключем** → нова сирота.
- Сьогоднішній `findBeerByNormalized` цифр не бачить (рев'ю 2, проба C). Після виправлення
  джерела аліасу (текст запиту) це вже не дає хибного ✅, але картки «#6» і «#7» досі ділять одну
  сироту, її бекоф і факти. Периферія бере сироту лише з `numericTokensCompatible`, як
  `ensureOrphan` (#617).
- **Влучання в аліас** повертає канонічний рядок і позначку `viaAlias: true`. Сирота не
  створюється. **Факти картки** (`fillOrphanFacts`) на аліасному влучанні **не пишуться**.

### `/enrich/candidates`

Для `viaAlias` рядок злінкований, тож без bid він не eligible, і пошуку немає.

### Репарація #384 через аліас

**Небезпека.** Сьогоднішній шлях `mayOverride` переписав би `untappd_id` **спільного**
канонічного рядка, хоча доказ стосується лише ключа однієї картки.

**Правило: суперечливий bid на аліасі стосується лише аліасу.**

- **`/enrich/candidates`.** Для `viaAlias` і `contradicts` рядок **eligible** незалежно від
  `refusesBidOverride(untappd_id_source)`. `isNotABeer` і `isEligible` лишаються як є.
- **`/enrich/result`.** Для `viaAlias` і `bid !== stored`:
  1. `resolveByBid` з тими самими аргументами, що й сьогодні.
  2. **Прийнято:** в одній транзакції видалити аліас ключа → `ensureOrphan` з парою картки →
     `applyLookupOutcome` на цій сироті. Bid нічий → сирота стає рядком цього bid; bid чийсь →
     злиття пише свіжий аліас. Далі `stampBidProvenance` і відповідь `matched`.
  3. **Відхилено:** аліас не змінюється, відповідь — збережений лінк канонічного рядка.
- **`viaAlias` і `bid === stored`** або без bid: відповідь `matched` зі збереженим лінком.

## Заявка → доказ

| Що записується або читається як факт | Що це доводить | Сила |
|---|---|---|
| Аліас «ключ картки = рядок Z» після злиття за опублікованим bid | магазин опублікував bid, гейт броварні `resolveByBid` його прийняв | сильна |
| Той самий аліас після пошукового злиття | конвеєр `lookupBeer` зматчив **саме цей текст** (`aliasSource` = вхід виклику). Ту саму заявку сирота мала б без конфлікту `UNIQUE`, і `/match` сьогодні читає її як `exact` | як у звичайного лінку |
| Аліас після злиття з крону (текст крана) | те саме, що й посилання крана з `confidence 1.0` (#366) | як у звичайного лінку |
| «Текст аліасу — той, який перевірено» | вхід `applyLookupOutcome`, а не текст рядка-сироти. Проба рев'ю 2 (C): з текстом сироти картка «Ґвара #6» отримала `exact` ✅ на рядок «#7» | доведено тестом |
| «Аліас стосується картки з іншими цифрами» | **нічого не доводить**: злиття бачило одну назву. Проби рев'ю: `Rochefort 10` на аліас «…8» (рев'ю 1) і `MJØD IS 2023` на аліас без року (рев'ю 2, B) давали хибний ✅ | заборонено ключем: цифри входять у ключ, рівність точна |
| «Ключ не належить жодному іншому рядку» | та сама пара **і** ті самі цифри; перевіряється в транзакції злиття **і** під час кожного читання | доведено на момент використання |
| «Аліас доводить рядок після зміни його bid» | **нічого не доводить**: аліас записано під старим bid | аліаси відкидаються (`recordLookupSuccess`, `pinMatch`, каскад злиття) |
| «Аліас не перекриється пізнішою сиротою з тим самим ключем» | проба 2026-09-14: 0 з 272 пар розширення збігаються з 1 491 нормалізованою парою кранів. Якщо перекриється — рядок важить більше, аліас не читається, картка йде в матчер | **виміряне прийняте обмеження** |
| Аліас після репарації #384 (периферія) | прийнятий bid для цього ключа; старий аліас видаляється в тій самій транзакції | сильна |

**Обмеження.**
- Сирота кранів з тим самим ключем вимикає аліас (рядок важить більше), і картка знову стає ⚪,
  доки злиття сироти не прибере рядок. Перевірку аліасу в `ensureOrphan` свідомо не додано: це
  змінило б поведінку кранів, а вона належить #632.
- Картка, чиї цифри не збігаються з цифрами аліасу точно (`Mjød` проти `Mjød 2021`), не
  отримує аліасу й проходить петлю, як до #614.
- Картка, яка має аліас на випите пиво Z, але крамниця публікує суперечливий bid, у клієнті
  **не** йде в дошук: `content/index.ts` не шле випите пиво на enrich (свідома обережність #384).
  Вона й далі показує Z з ✅, доки аліас не скасують.

## Скасування хибного аліасу

```
sudo -u warsaw-beer-bot bash -lc "sqlite3 /var/lib/warsaw-beer-bot/bot.db \
  \"DELETE FROM beer_aliases WHERE normalized_brewery = '<…>' AND normalized_name = '<…>' AND name_digits = '<…>'\""
```

- **Після скасування** наступне завантаження картки знову пройде петлю один раз. Якщо злиття
  знову поставить той самий аліас, дефект у доказі (bid крамниці чи пошук), а не в пам'яті.
- **Інструмента немає** (YAGNI), рецепт іде в `spec.md` поруч із `merged_at = NULL`.
- **`pinMatch`** зі зміною bid відкидає аліаси рядка сам (див. «Запис»).

## Тести

Кожен тест доводиться мутацією: видалити рядок коду → тест падає. Сіди мають видимі значення, а
не `null` (`feedback_stub_defaults_hide_mutations`).

**Нормалізація (`normalize.test.ts`)**
- `nameDigits`: відсортовані числові токени; порожньо без цифр; специфікація не потрапляє.

**Storage (`beers.test.ts`, `pin-match.test.ts`, `schema.test.ts`)**
- Унікальність — трійка: однакова пара з різними `name_digits` дозволена, з однаковими — ні.
- Злиття пише аліас з `aliasSource` (якщо передано) або з тексту сироти, з `name_digits`.
- Близнюк з тією самою парою **і** тими самими цифрами блокує аліас; близнюк з іншими цифрами — ні.
- Конфлікт ключа переписує `beer_id` на новий рядок; аліаси «8» і «10» однієї пари живуть поруч.
- Злиття злінкованого рядка з аліасами **не** переносить їх на власника bid.
- `recordLookupSuccess` з іншим bid відкидає аліаси; з тим самим — лишає; на `UNIQUE` — відкат.
- `pinMatch` з новим bid на рядку з аліасами видаляє їх.
- `loadAliases`: не читає аліас рядка без `untappd_id`; не читає аліас, чий ключ тримає рядок
  `beers` з тими самими цифрами; **читає**, коли пару тримає близнюк з іншими цифрами.

**Домен (`lookup-outcome.test.ts`, `match-list.test.ts`, `catalog-cache.test.ts`)**
- `applyLookupOutcome` зливає сироту, створену іншою карткою, і пише аліас з тексту **виклику**
  (сценарій «Ґвара #6 / #7»).
- Аліасне влучання → `exact`, `is_drunk`, `user_rating`, канонічні назва й рейтинг, бюджет
  фолбеку не витрачено.
- Картка з іншими цифрами (`8` проти `10`, без цифр проти `10`, `2023` проти без року) аліасом
  **не** влучає: ні `exact`, ні `is_drunk`.
- Кеш будує `aliases` з `loadAliases`, а `prepared` аліасів не містить.
- Інтеграційний: злиття на справжній БД → кеш → `matchBeerList` дає `exact` ✅.

**Підключення (`match.test.ts`, `mcp.test.ts`)**
- `POST /match` і MCP `match_beers` після злиття дають точний збіг зі статусом «пив» для картки
  крамниці. Без передачі `aliases` у `matchBeerList` тест падає.

**`/enrich/*` (периферія, `enrich.test.ts`)**
- `ensureBeerRow` не віддає картці «#7» сироту картки «#6».
- Картка з аліасом → канонічний рядок, нова сирота не створюється, `eligible: false`.
- Картка з аліасом і суперечливим bid → `eligible: true`, навіть коли канонічний рядок
  `checkin`/`curated`.
- `/enrich/result`, bid прийнято: старий аліас видалено; новий аліас дивиться на рядок з bid;
  `untappd_id` і `untappd_id_source` канонічного рядка **не змінилися**.
- `/enrich/result`, bid відхилено: аліас і канонічний рядок без змін.

**Наскрізний тест петлі (API, периферія)**
- `/enrich/candidates` → `/enrich/result` з bid → злиття → `POST /match` з токеном дає `exact`,
  `is_drunk: true`, `user_rating`. На поточному `main` тест мусить падати.

**Міграція.** v32 на свіжій БД і на копії прод-БД без помилок. Таблиця порожня, наявні дані не
змінюються.

### Перше рев'ю

1. **Числові близнюки — хибний ✅.** Аліас картки «…8» ставав точним кандидатом і для картки «…10».
   Реплей: `ROCH / Trappistes Rochefort 10` → рядок 8, `exact`, ✅. → Аліас винесено з каталогу
   матчера в окрему перевірку з правилом цифр.
2. **Аліаси йшли за рядком, чий bid переписано.** → Перенесення прибрано; зміна bid відкидає аліаси.
3. **Аліас звужував неточний пошук** для своєї етикетки. → Зникає разом з п. 1.
4. **Три інші шляхи видалення рядків** — не блокер.
5. **«Мертвий» аліас** поруч зі свіжим рядком тієї самої пари. → Правило «рядок важить більше».

### Друге рев'ю

Переробка (коміти `7301421`…`0285628`) закрила п. 1–3 першого рев'ю для прямого зіставлення, але
правило цифр порівнювало картку з **сумісними** цифрами назви аліасу, а ключ аліасу цифр не мав.
Знайдено й підтверджено пробою рецензента (сценарії A–C):

- **C — blocker, досяжний без периферії.** `ensureBeerRow` цифр не бачить: картка «Ґвара #7»
  дістала сироту картки «#6», пошук «#7» її злив, а аліас записав текст сироти «#6». Картка «#6» →
  рядок «#7» `exact` ✅. → Аліас пише **текст виклику** (`aliasSource`).
- **B — хибний ✅ через рік.** Аліас `MJØD IS` на вінтаж 2021; картка `MJØD IS 2023` — «сумісна»
  (рік лише в одній назві) → `exact` ✅ на 2021. Матчер у такій ситуації відмовляє
  (`matcher.ts`, «do not cross-match vintages»). → Цифри в ключі, рівність точна.
- **A — петля для близнюків однієї крамниці.** Ключ без цифр вміщав один аліас на «8» і «10», а
  «рядок важить більше» гасив аліас сиротою-близнюком → аліас стрибав між рядками. → Цифри в
  ключі й у перевірках «рядок тримає ключ».
- Перевірено й коректно: код `SQLITE_CONSTRAINT_UNIQUE` проходить крізь транзакцію
  `recordLookupSuccess`; інших записів `untappd_id`, що мали б відкидати аліаси, немає; тести
  `/match` і MCP ідуть через справжній кеш.

Урок обох рев'ю один: **ключ, збудований нормалізатором із втратами, треба або робити без втрат,
або доводити кожне порівняння, яке через нього проходить.** Двічі латали порівняння — двічі
знаходився новий шлях у втрачену частину.
