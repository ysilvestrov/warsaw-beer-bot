# Дизайн — пам'ять злиття для карток крамниць: `/match` впізнає картку після першого пошуку (закриває #614)

**Дата:** 2026-09-14. Переглядалося дев'ять разів того ж дня після наскрізних рев'ю ядра й брейншторму — див. «Рев'ю ядра».
**Issue:** [#614](https://github.com/ysilvestrov/warsaw-beer-bot/issues/614). Бід-резолв → злиття → `/match` знову
`null`: ті самі пива шукаються в сесії Untappd на кожному завантаженні, а бейдж після пошуку не
показує статусу «пив».
**Пов'язані:**
- #366 — пам'ять злиття для кранів, `match_links.merged_at`;
- #384 — ідентичність за опублікованим bid;
- #632 — петля злиттів на шляху кранів, виділено;
- #633 — `/match` приймає опублікований bid, виділено;
- #636 — правило ідентичності «різні цифри з обох боків — різні пива», виділено;
- #637 — втрати тексту в адаптері Flasker (`IS`, усе після маркера ABV), виділено;
- #618 — назва Untappd окремо від ключа матчингу.

## Проблема (доведена)

### Петля

Назва картки в крамниці часто не збігається з назвою рядка в каталозі. Тоді на **кожне**
завантаження сторінки:

1. `POST /match` повертає `matched_beer: null`, і картка стає сиротою.
2. `/enrich/candidates` → `ensureBeerRow` створює **новий** рядок-сироту з парою картки
   (`untappd_lookup_count = 0`, тобто `eligible: true`).
3. Розширення шукає пиво в сесії Untappd користувача. Далі `/enrich/result`: bid крамниці
   приймається (`resolveByBid`) або його знаходить пошук. Bid уже належить іншому рядку, тож
   спрацьовує `SQLITE_CONSTRAINT_UNIQUE` → `mergeIntoCanonical` → сироту **видалено**.
4. Клієнт малює ⭐ (`setEnriched`) і нічого не кешує. Сервер теж нічого не запам'ятовує для
   `/match`: `merged_at` (#366) живе лише на `match_links`, а їх читає тільки інжест кранів.

Після кроку 4 стан такий самий, як до кроку 1. Бекоф петлю не зупиняє, бо щоразу рахує
новий рядок.

### Статус «пив» губиться

Відповідь `/enrich/result` — це `{status, untappd_id, rating_global}`. `setEnriched` малює ⭐
лише з цих полів. Навіть коли пошук правильно знаходить випите пиво, бейдж не показує ні ✅,
ні особистої оцінки. Такі поля за побудовою є лише у відповіді `/match`.

### Виміри (2026-09-14, прод-БД лише читання, журнал за 14 днів)

- **Злиття на шляху розширення з bid:** 39 злиттів на 16 bid, з них 23 повтори
  (5120103 `Copper Head. Beer Workshop / Red Mexican` — 7; 5794217 `THE WORST BREWERY IN THE WORLD /
  THE WORST LAGER` — 7; 5001305 — 6; 5561840 — 4).
- **Інші злиття:** ≈15 поза вікнами інжесту без bid (шлях розширення з пошуком). Ще 84 у вікнах
  інжесту кранів — окремий механізм, #632.
- **Випадок користувача.** Flasker, `VARVAR BLACK BEAN IS 11% 0.33л` → `parseTitle`
  `{brewery: "VARVAR", name: "BLACK BEAN IS", abv: 11}`. Рядок 2815 `Varvar Brew / Black Bean`
  (bid 3548624) — 4 чекіни, оцінка 4.5. `/match` для картки → `null`; для `VARVAR / BLACK BEAN` →
  2815 `exact` ✅ 4.5 (суфікс `IS` — #637).
- **Нормалізатор — не ідентичність** (#636): серед 935 пар злінкованих рядків з різними bid, але
  однаковим нормалізованим ключем, 604 різняться цифрами з обох боків, 153 — цифрою з одного боку,
  178 — словами, які нормалізатор теж викидає.
- **Текст картки — теж не вся ідентичність.** Адаптер Flasker обрізає назву на першому маркері ABV
  чи об'єму: `LEFFE BLONDE 0.0% 0.33л` і `LEFFE BLONDE 6.6% 0.33л` дають однаковий текст
  `LEFFE / BLONDE`, різниться лише `abv`; `Xmas Eve 10% [2025]` і `[2024]` дають однаковий текст **і**
  ABV (#637).

### Проба рішення (до дизайну)

Аліас «картка → `id` канонічного рядка» на прод-каталозі дає `exact` з особистим статусом:
`VARVAR / BLACK BEAN IS` → 2815 `exact` ✅ 4.5; Red Mexican → 23000; The Worst Lager → 23047.
Ключ, яким проба це робила (нормалізована пара), виявився хибним — див. «Рев'ю ядра».

## Рішення

Злиття запам'ятовує **картку, яку перевірив пошук**, — текст броварні, текст назви й ABV — як
**аліас** канонічного рядка. `/match` і MCP перевіряють аліас **перед** матчером: канонізований текст
картки й її ABV мають **точно** дорівнювати ключу аліасу. Влучання дає точний збіг з особистим
статусом. Пошук, створення рядка й злиття більше не повторюються. Зміна лише серверна.

**Чому ключ — усе, що надсилає розширення.** Петля #614 — це **та сама картка** з **тим самим**
`brewery`, `name` і `abv` на кожному завантаженні, а доказ злиття стосується лише цієї картки.
Нормалізатор кандидатів губить текст (три рев'ю); текст без ABV губить ABV-близнюків (четверте
рев'ю). Ключ з усіх полів картки не губить нічого з того, що сервер узагалі отримує.

**Межа (узгоджено з користувачем, 2026-09-14).** Аліас точний настільки, наскільки точна картка від
адаптера. Те, що адаптер обрізав до надсилання (вінтаж після ABV, самотнє `IS`), на сервері
нерозрізненне для будь-якого ключа; такі втрати лагодяться в адаптері (#637), не тут.

**Рівень доказу — ✅ для обох шляхів злиття** (рішення користувача).
- **Злиття за опублікованим bid:** магазин опублікував bid, гейт броварні його прийняв.
- **Злиття з пошуку:** якби bid не належав уже іншому рядку, сирота з цією самою карткою просто
  отримала б `untappd_id`, і `/match` читав би її як `exact`.

Злиття не повинно робити відповідь слабшою, ніж без нього, і не повинно робити її сильнішою для
картки, про яку воно нічого не доводило. Звідси:
- ключ — точна картка (текст + ABV), без нормалізації;
- картка аліасу — та, яку шукав виклик, а не рядок-сирота, що міг прийти від іншої картки;
- аліас доводить лише той bid, під яким його записано.

## Канонізація картки: `cardText`, `cardAbv`

`src/domain/card-text.ts`:

```ts
export function cardText(s: string): string {
  return s.normalize('NFC').replace(/\s+/gu, ' ').trim().toLowerCase();
}

export function cardAbv(abv: number | null | undefined): string {
  return abv == null || !Number.isFinite(abv) ? '' : String(Math.round(abv * 100) / 100);
}
```

- **`cardText` змінює лише представлення:** NFC, пробіли (`\s` покриває U+00A0, U+202F, U+FEFF),
  регістр. Цифри, дужки, пунктуація, стиль і шум броварні лишаються. Символи, які NFC не зводить
  (повноширинні, U+200B, м'який перенос), дають інший текст — промах, а не хибний ✅.
- **`cardAbv`:** санітизований ABV картки до сотих; відсутній ABV — `''`, окреме значення (не NULL,
  бо NULL у `UNIQUE` SQLite не рівний сам собі). `0` — справжнє значення (#322).
- **Окремий модуль, не `normalize.ts`,** щоб його не сплутали з нормалізатором кандидатів.

## Дані: таблиця `beer_aliases` (міграція v32)

```sql
CREATE TABLE beer_aliases (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  beer_id      INTEGER NOT NULL REFERENCES beers(id) ON DELETE CASCADE,
  brewery      TEXT NOT NULL,   -- сирий текст броварні з картки
  name         TEXT NOT NULL,   -- сирий текст назви з картки
  brewery_text TEXT NOT NULL,   -- cardText(brewery)
  name_text    TEXT NOT NULL,   -- cardText(name)
  abv_key      TEXT NOT NULL,   -- cardAbv(abv): '' коли ABV картки відсутній
  created_at   TEXT NOT NULL,
  UNIQUE (brewery_text, name_text, abv_key)
);
CREATE INDEX idx_beer_aliases_beer ON beer_aliases(beer_id);
```

- **Ключ** — `(brewery_text, name_text, abv_key)`. `/match` і `/enrich/*` отримують від розширення одні
  й ті самі `brewery`/`name`/`abv` для однієї картки: `raw` для `/match` і для сиріт будується з одного
  об'єкта після `loadCardDetails`, ABV — через `usableAbv` (`extension/src/content/index.ts`);
  `/enrich/candidates` повертає `brewery`/`name` без змін, клієнт шле їх у `/enrich/result`
  (`extension/src/content/enrich.ts`). Перевірено рев'ю 3 і 4. **Виняток — картки-близнюки з однаковим текстом на
  одній сторінці:** клієнт тримає одну картку на текст (`byPair`), тож `/enrich/result` може нести ABV іншої картки;
  аліас тому бере ABV пошуку, і розбіжність дає лише промах (рев'ю 5).
- **Міграція v32 ще не застосована ніде** (прод на версії 31), тож колонки змінюються в самій v32.
- **Бекфілу немає.** Таблиця заповнюється першим же злиттям (як `merged_at`, #366).

## Запис

### `mergeIntoCanonical(db, orphanId, canonicalId, at, aliasSource?)`

`aliasSource?: { brewery: string; name: string; abv?: number | null }`. У тій самій транзакції, **до**
`DELETE FROM beers`:

1. **Картка аліасу** — `aliasSource` (картка, яку шукав виклик), а без нього — сирі `brewery`/`name`/
   `abv` рядка-сироти. `applyLookupOutcome` передає свій `input` завжди:
   - `/enrich/result`, шлях bid — `{ brewery, name, abv, byBid: true }` картки з тіла запиту (ідентичність дає
     опублікований bid; `byBid` не ставить жоден інший шлях);
   - `/enrich/result`, шлях пошуку — `{ brewery, name }` картки і **ABV, з яким реально йшов пошук** (`row.abv`):
     сирота могла взяти ABV іншої картки з тим самим текстом, і пошук довів «текст + ABV рядка», а не ABV тіла
     (рев'ю 5);
   - крон (`enrichOneOrphan`) — `{ brewery, name, abv }` самої сироти.
2. **Аліас — лише коли злита сирота і є цією карткою.** Якщо `aliasSource` передано, аліас пишеться лише
   коли `cardText(brewery)` і `cardText(name)` сироти дорівнюють полям `aliasSource`. Інакше аліасу немає.
   **Виняток — доказ bid** (`aliasSource.byBid`, рев'ю 11, R1): `resolveByBid` читає лише поля картки з тіла запиту
   (`shopBrewery/shopName/shopAbv`) і сам bid, текст рядка в доказ не входить — аліас пишеться, хоч би яке написання
   мала сирота тієї самої нормалізованої пари, на яку ліг bid. Без винятку bid крамниці лягав на сироту «Browar Varvar /
   Black Bean IS», а аліас картки «VARVAR / BLACK BEAN IS» лишався на старому bid — назавжди хибний ✅. ABV не
   порівнюється: шлях пошуку й так передає `row.abv` (ABV, з яким ішли і `lookupBeer`, і веб-фолбек), крон — поля
   самого рядка, а доказ шляху bid узятий з полів картки (`shopBrewery/shopName/shopAbv`), тоді як репарація #384
   зливає злінкований рядок з ABV з Untappd — порівняння ABV забрало б аліас саме там. Причина: `ensureBeerRow` шукає рядок нормалізатором, тож сирота могла прийти від іншої картки з тією самою
   нормалізованою парою («Gwara #6» для запиту «Gwara #7»), а частина доказу йшла з полями сироти, а не картки:
   `lookupBeer` — з `row.abv`, веб-фолбек (`webFallback` → `getBeer`) — з текстом і ABV рядка. Коли сирота — інша
   картка, доказ неоднозначний, і промах безпечніший за аліас (рев'ю 5 і 6).
3. **Порожній текст — без аліасу.** Якщо `cardText(brewery)` або `cardText(name)` порожні, аліас не
   пишеться.
4. **Запис:** `INSERT … ON CONFLICT(brewery_text, name_text, abv_key) DO UPDATE SET beer_id, brewery,
   name, created_at`. Той самий ключ, що вже вказував на інший рядок, переходить на новий.
5. **Аліаси рядка, що зливається, не переносяться** — їх забирає `ON DELETE CASCADE`.

### `recordLookupSuccess(db, beerId, r, at, aliasSource?)` переносить аліас ключа картки

Конфлікт двох доказів для тієї самої картки (давнє злиття сказало Z, новіший лінк — X) розв'язує **запис**, а не
читання. `applyLookupOutcome` передає свій `input` і сюди. У тій самій транзакції, після `UPDATE`:
1. ключ — `cardText(brewery)`, `cardText(name)`, `cardAbv(abv)` картки `aliasSource`; порожній текст — нічого;
2. **лише коли рядок, що лінкується, і є цією карткою** (той самий `cardText` броварні й назви) — те саме правило,
   що в `mergeIntoCanonical`, з тієї самої причини (рев'ю 6); на шляху bid (`byBid`) — без цієї умови, як і в
   злитті (рев'ю 11, R1);
3. наявний аліас цього ключа **переходить** на рядок (`UPDATE … SET beer_id`), як `ON CONFLICT` у злитті;
   **нового аліасу не створює**: без давнього злиття картку відповідає рядок з її текстом, як до #614.

Шляхи: `/enrich/result` bid і пошук (картка, ABV пошуку на шляху пошуку), крон (сам рядок — той самий доказ, що
й пошуковий шлях, і та сама політика «найсвіжіший доказ», що в `ON CONFLICT` злиття). `upsertBeerByBid` (синк
чекінів, `/import`) і `pinMatch` лінкують нормалізовану пару чи кран, не картку, — аліас не переносять (обмеження
нижче).

Під час читання перевірок «цю картку вже тримає інший рядок» немає.

### Зміна `untappd_id` рядка відкидає його аліаси

`dropAliasesOnRelink(db, beerId, newBid)` видаляє аліаси рядка, якщо його `untappd_id` **IS NOT**
новий bid (тобто й коли він `NULL` — рядок, чий bid хтось обнулив вручну). Викликається:
- у `recordLookupSuccess` у транзакції з `UPDATE` (на `UNIQUE` — відкат, аліаси забирає каскад злиття);
- у `pinMatch`, гілка «новий bid»;
- у `upsertBeerByBid`, гілка `resolvableOrphan` — рядок з обнуленим вручну bid (синк чекінів, `/import`) інакше
  оживляв старі аліаси під новим bid (рев'ю 9, M2).

## Читання: аліас перед матчером

### Завантаження (`loadAliases`)

`SELECT a.beer_id, a.brewery_text, a.name_text, a.abv_key FROM beer_aliases a JOIN beers b ON b.id =
a.beer_id WHERE b.untappd_id IS NOT NULL` — аліас на рядок без `untappd_id` не читається.

### Індекс у кеші каталогу: `buildAliasIndex(aliasRows)`

- Мапа «`brewery_text|name_text|abv_key` → `beerId`» з усіх аліасів на злінковані рядки. **Аліас відповідає за свій
  точний ключ завжди**; каталог індекс не читає.
- **Чому без правила «рядок каталогу важить більше».** Три його версії під час читання вгадували конфлікт доказів
  і кожна давала хибну ідентичність: за текстом — сирота вимикала аліас (проби `periph-*`); лише злінковані —
  злінкований ABV-близнюк вимикав аліас, і репарація #384 ганяла пінг-понг злиттів з переїздом чекінів (рев'ю 9,
  M1); з ABV рядка — ABV злінкованого рядка береться з Untappd (`COALESCE(r.abv, abv)`), а ключ аліасу — з картки
  крамниці, тож результат вирішував збіг чисел: правильний bid крамниці не переносив картку (назавжди хибний ✅,
  рев'ю 10, N1), а близнюк з Untappd-ABV, рівним ABV іншої картки, повертав пінг-понг (N2). Конфлікт, який
  правило намагалося побачити, тепер розв'язує запис (`recordLookupSuccess`, `ON CONFLICT` злиття).
- Каталог матчера аліасів не містить; `byId` — лише рядки `beers`. `/match` і MCP передають `aliases` у
  `matchBeerList`. Аліаси читаються тим самим знімком, що й каталог.

### `matchBeerList`

Для кожної картки, **до** `matchPrepared`:

1. якщо `cardText(brewery)` або `cardText(name)` порожні — аліас не шукається;
2. ключ = `cardText(brewery)|cardText(name)|cardAbv(abv)`; в індексі є аліас **і** `byId` має його
   `beerId` → `exact`: `is_drunk`, `user_rating`, `searched: true`; матчер і бюджет фолбеку не
   чіпаються;
3. інакше — матчер, як сьогодні.

Приклади (сценарії чотирьох рев'ю):
- `ROCH / Trappistes Rochefort 10` проти аліасу `… Rochefort 8` → інший текст → матчер.
- `VARVAR / MJØD IS 2023` проти аліасу `VARVAR / MJØD IS` → інший текст → матчер.
- `Finback / BQE Nitro (2024 …)` проти аліасу `(2023 …)` → інший текст → матчер.
- `Browar / Amigo Mate Bananowe` проти злиття з порожньою броварнею → аліасу не існує.
- `LEFFE / BLONDE` abv 6.6 проти аліасу `LEFFE / BLONDE` abv 0 → інший ABV → матчер.
- `LEFFE / BLONDE` без ABV проти аліасу з abv 0 → інший ключ → матчер.
- `varvar /  Black  Bean IS` abv 11 проти аліасу `VARVAR / BLACK BEAN IS` abv 11 → той самий ключ → аліас.

## `/enrich/*` (периферія)

Проби засновків (2026-09-14, справжні роути, `scratchpad/periph-*.mts`) показали, що без периферії ядро
**регресує**: будь-яка сирота з текстом картки вимикає аліас, а `/enrich/candidates` створює таку сироту для
самої картки з аліасом у двох нормальних сценаріях:
- **повторний раунд тієї самої картки** — перший `/match` після злиття віддає застарілий знімок кешу (SWR) з
  `null`, розширення знову шле картку в `/enrich/candidates`, `findBeerByNormalized` канонічного рядка не
  бачить, створюється сирота → `/match` віддає її `exact` без ✅ (`periph-e2e`, кроки 4–6);
- **суперечливий bid на картці з аліасом** — розширення шле зматчену картку в дошук, коли bid крамниці
  суперечить збігу (`extension/src/content/index.ts`, `bidContradicts`, крім випитих) → та сама сирота; після
  відхиленого bid вона лишається (`periph-premise`, кроки 2–5).

### `ensureBeerRow`

Порядок: **аліас з тим самим ключем картки** → рядок `beers` з нормалізованою парою → нова сирота.
- **Аліас раніше за пару** (рев'ю 11, R3). До того пара йшла першою, і картка з аліасом отримувала рядок близнюка
  тієї самої пари — сироту з іншим написанням або злінкований ABV-близнюк. Суперечливий bid картки перелінковував
  рядок близнюка, bid близнюка — назад: пінг-понг на кожному завантаженні (проба `review10/writetime`, PD). `/match`
  і так відповідає аліасом першим; сирота пари лишається крону.
- Ключ — той самий, що в `/match`: `cardText(brewery)`, `cardText(name)`, `cardAbv(abv)` **сирого** ABV з тіла
  запиту (не санітизованого), лише для аліасу на рядок з `untappd_id` (`findAliasTarget`).
- Влучання повертає канонічний рядок з `viaAlias: true`; сирота не створюється; факти картки не пишуться
  (`fillOrphanFacts` злінкованих рядків і так не чіпає).
- Інший ABV — інший ключ: ABV-близнюк отримує власну сироту; аліас від неї не залежить (індекс не читає
  каталог).
- Те, що `findBeerByNormalized` не бачить цифр, лагодить #636.

### `/enrich/candidates`

- `viaAlias` без bid або з тим самим bid — рядок злінкований, `eligible: false`.
- `viaAlias` + суперечливий bid — **eligible незалежно від `refusesBidOverride`**: суперечність стосується
  аліасу, а не провенансу канонічного рядка (канонічний рядок випитого пива зазвичай `checkin`). Вето
  `not_a_beer` і бекоф канонічного рядка діють, як для репарації #384 злінкованого рядка (свідома
  консервативність: `recordLookupSuccess` ставить `untappd_lookup_at`, тож нещодавно збагачений канонічний
  рядок не дошукується до кінця свого бекофу).

### Репарація #384 через аліас (`/enrich/result`)

Суперечливий bid на аліасі стосується лише аліасу, канонічний рядок не змінюється ніколи:
- `viaAlias` + `bid !== stored` → `resolveByBid` з полями картки (незалежно від `refusesBidOverride`).
- **Прийнято** — в одній транзакції: `ensureOrphan` з карткою → `applyLookupOutcome(orphan, bid, input = картка з
  `byBid`)`. `ensureOrphan` повертає наявну **сироту** пари картки (з іншим написанням — bid картки лягає на неї, як
  на `main` для будь-якої картки з bid, #636) або вставляє нову; **злінкований рядок пари не повертає ніколи**, тож
  bid ABV-близнюка не переписується. Аліас ключа переходить разом із
  доказом: bid чийсь → злиття в його власника (`ON CONFLICT`); bid нічий → сирота стає рядком з цим bid
  (`recordLookupSuccess`). Окремого видалення аліасу немає (до рев'ю 10 — `deleteAlias`). Транзакція потрібна, щоб
  збій запису лінка не лишив сироти з текстом картки. Відповідь `matched` з новим bid, `stampBidProvenance`.
- **Відхилено** — без змін: `matched` зі збереженим лінком, сироти немає, аліас на місці.
- `viaAlias` + `bid === stored` або без bid → `matched` зі збереженим лінком.

**Обмеження.**
- **Аліас допомагає лише тій самій картці** (текст + ABV). Інше написання того самого пива потребує
  власного злиття. Ширше зіставлення — справа матчера (#636, #618).
- **Втрати адаптера** (#637) роблять різні товари однією карткою; аліас успадковує цю неточність, як і
  матчер.
- **Нестабільна картка** (провал деталей товару змінює броварню чи ABV) — промах і одне повторне
  проходження петлі.
- **Картки-близнюки з однаковим текстом на одній сторінці** (6.1% і 0.5%) ділять у клієнті одну сироту й один
  пошук за раз; аліас записується з ABV пошуку, тож друга картка отримує свій аліас лише власним злиттям.
- **Картка з аліасом на випите пиво Z і суперечливим bid** у клієнті не йде в дошук (свідома
  обережність #384); показує Z з ✅, доки аліас не скасують.
- **`scripts/pin-match.ts`** працює в окремому процесі, його бамп версії каталогу до бота не доходить:
  відкинутий аліас лишається в індексі до TTL кешу (5 хв). Так поводяться й інші записи цього скрипта.
- **Гонка під час hydrate у репарації аліасу** (рев'ю 9, m1). Між `await resolveByBid` і транзакцією `/enrich/candidates`
  картки-близнюка може створити сироту з тією самою парою; `ensureOrphan` поверне її, і bid картки ляже на рядок
  близнюка. Той самий клас, що й відоме «картки з однаковою парою ділять сироту» (#636).
- **ABV картки поза межами `sanitizeAbv`** (150, -1) на шляху пошуку: аліас пишеться з `row.abv` = NULL → ключ `''`,
  а `/match` шукає `'150'` — картка й далі проходить петлю (рев'ю 9, m2). Не регресія: без #614 вона петляла так само.
- **Лінк, що доводить не картку, аліас не переносить** (рев'ю 10, N3). Синк чекінів і `/import` (`upsertBeerByBid`),
  `pinMatch` лінкують нормалізовану пару чи кран: картка й далі показує ціль аліасу, навіть коли рядок з її текстом
  отримав інший bid, — можлива втрата правдивого ✅, не хибний ✅.
- **Аліас не пам'ятає, чим доведений** (рев'ю 11, R2). Пошук (крон чи шлях пошуку `/enrich/result`) на рядку самої
  картки з тим самим текстом і ABV переносить аліас, доведений bid крамниці, на свою здогадку. Наступне завантаження
  з опублікованим bid повертає його (репарація #384); крамниця без bid чи випите пиво (у дошук не йде) лишають
  картку на здогадці. Лікування — колонка джерела доказу в аліасі; окремий issue.
- **Кожна наступна зміна bid крамниці для картки з аліасом дає новий рядок картки** (наслідок R3). Злінкований рядок,
  на який указує аліас, репарація не перелінковує (`ensureOrphan` повертає лише сироту), тож попередній рядок
  лишається з попереднім bid. Аліас указує на останній; старий рядок бачить лише матчер інших написань (#636).

## Рев'ю ядра (2026-09-14)

Чотири наскрізні рев'ю поспіль знаходили хибний ✅ **одного роду**: ключ аліасу не містив частину

4. **Брейншторм** переформулював корінь: нормалізатор — ключ пошуку кандидатів, не ідентичність

7. **Сфокусоване рев'ю фіксу (шосте).** ABV закрито, але веб-фолбек (`webFallback` → `getBeer`) шукав текстом

8. **Проби засновків периферії.** Ядро без периферії регресує: сирота з текстом картки вимикала аліас. Три

   близнюка дорівнював ABV іншої картки; N3 — синк чекінів не перебивав аліас. Третє уточнення одного правила

11. **Повторне рев'ю раунду 10 (одинадцяте).** Перенесення під час запису працює, але: R1 — умова «рядок = картка»
