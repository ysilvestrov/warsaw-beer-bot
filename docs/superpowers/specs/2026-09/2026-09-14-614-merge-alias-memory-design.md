# Дизайн — пам'ять злиття для назв з крамниць: `/match` впізнає картку після першого пошуку (закриває #614)

**Дата:** 2026-09-14 (переглянуто того ж дня після наскрізного рев'ю ядра — див. «Рев'ю ядра»)
**Issue:** [#614](https://github.com/ysilvestrov/warsaw-beer-bot/issues/614). Бід-резолв → злиття → `/match` знову
`null`: ті самі пива шукаються в сесії Untappd на кожному завантаженні, а бейдж після пошуку не
показує статусу «пив».
**Пов'язані:**
- #366 — пам'ять злиття для кранів, `match_links.merged_at`;
- #384 — ідентичність за опублікованим bid;
- #617 — `numericTokensCompatible`, правило сумісності числових токенів назви;
- #632 — петля злиттів на шляху кранів, виділено;
- #633 — `/match` приймає опублікований bid, виділено;
- #618 — назва Untappd окремо від ключа матчингу.

## Проблема (доведена)

### Петля

Назва картки в крамниці часто не збігається з назвою рядка в каталозі. Тоді на **кожне**
завантаження сторінки:

1. `POST /match` повертає `matched_beer: null`, і картка стає сиротою.
2. `/enrich/candidates` → `ensureBeerRow` створює **новий** рядок-сироту з парою картки
   (`untappd_lookup_count = 0`, тобто `eligible: true`).
3. Розширення шукає пиво в сесії Untappd користувача. Далі `/enrich/result`: bid крамниці
   приймається (`resolveByBid`) або його знаходить пошук. Bid уже належить іншому рядку, тож
   спрацьовує `SQLITE_CONSTRAINT_UNIQUE` → `mergeIntoCanonical` → сироту **видалено**.
4. Клієнт малює ⭐ (`setEnriched`) і нічого не кешує. Сервер теж нічого не запам'ятовує для
   `/match`: `merged_at` (#366) живе лише на `match_links`, а їх читає тільки інжест кранів.

Після кроку 4 стан такий самий, як до кроку 1. Бекоф петлю не зупиняє, бо щоразу рахує
новий рядок.

### Статус «пив» губиться

Відповідь `/enrich/result` — це `{status, untappd_id, rating_global}`. `setEnriched` малює ⭐
лише з цих полів. Навіть коли пошук правильно знаходить випите пиво, бейдж не показує ні ✅,
ні особистої оцінки. Такі поля за побудовою є лише у відповіді `/match`.

хибним — див. «Рев'ю ядра».

## Рішення

Злиття запам'ятовує пару «броварня + назва» сироти як **аліас** канонічного рядка. `/match` і
MCP перевіряють аліас **перед** матчером: пара картки, рівна парі аліасу, з сумісними цифрами в
назві, дає точний збіг з особистим статусом. Пошук, створення рядка й злиття більше не
повторюються. Зміна лише серверна: розширення не змінюється, ефект настає після деплою.

**Рівень доказу — ✅ для обох шляхів злиття** (рішення користувача, 2026-09-14).
- **Злиття за опублікованим bid:** магазин опублікував bid, гейт броварні його прийняв. Це
  сильніше за збіг назв.
- **Злиття з пошуку:** якби bid не належав уже іншому рядку, сирота з цією самою парою просто
  отримала б `untappd_id`, і `/match` сьогодні читав би її як `exact`.

Злиття не повинно робити відповідь слабшою, ніж без нього. І не повинно робити її **сильнішою**
для картки, про яку злиття нічого не доводило — звідси правило цифр і правило «аліас доводить
лише той bid, під яким його записано».

### Поза скоупом

- **#632** — петля злиттів на шляху кранів. Спільний `ontap_ref` скидає `merged_at`, механізм
  інший. Цей дизайн не змінює `refresh-ontap` і `ensureOrphan`.
- **#633** — bid у `/match`: точний бейдж без жодного пошуку. Потрібен реліз розширення.
- **#618** — назва Untappd як аліас. Таблиця з цього дизайну може прийняти й таке джерело,
  але тут його немає (YAGNI).
- **Суфікс `IS` у назвах Flasker.** Фікс парсера закрив би лише такі картки. Red Mexican
  ламається без жодного суфікса.

## Дані: таблиця `beer_aliases` (міграція v32)

```sql
CREATE TABLE beer_aliases (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  beer_id            INTEGER NOT NULL REFERENCES beers(id) ON DELETE CASCADE,
  brewery            TEXT NOT NULL,   -- як надіслала картка (сирий текст)
  name               TEXT NOT NULL,
  normalized_brewery TEXT NOT NULL,
  normalized_name    TEXT NOT NULL,
  created_at         TEXT NOT NULL,
  UNIQUE (normalized_brewery, normalized_name)
);
CREATE INDEX idx_beer_aliases_beer ON beer_aliases(beer_id);
```

- **Нормалізована пара** — ключ пошуку. Ті самі `normalizeBrewery`/`normalizeName`, якими
  `ensureBeerRow` рахував пару сироти з того самого сирого тексту картки, тож `/match` для тієї
  самої картки отримує рівно цей ключ.
- **Сира назва** потрібна для правила цифр: `normalizeName` відкидає числові токени, тому
  порівнювати їх можна лише за сирим текстом (`numericTokensCompatible`, #617).
- **Сира броварня** зберігається для аудиту й рецепта скасування.
- **Бекфілу немає.** Сирота видаляється при злитті, тож відновлювати пару нема з чого. Таблиця
  заповнюється сама, щойно сторінку завантажать наступного разу (так само, як `merged_at`, #366).

## Запис

### `mergeIntoCanonical`

У тій самій транзакції, **до** `DELETE FROM beers`:

1. **Пара сироти стає аліасом**, але лише коли **жоден інший рядок `beers`** (крім сироти) не
   має цієї нормалізованої пари.
   - Причина: ontap-сирота буває вінтажним близнюком злінкованого рядка. `normalizeName`
     відкидає числові токени, тож «Rochefort 8» і «Rochefort 10» мають одну пару.
   - Для сироти з enrich-роуту умова виконується завжди: `ensureBeerRow` знайшов би наявний
     рядок з цією парою і не створив би сироту.
2. **Запис:** `INSERT … ON CONFLICT(normalized_brewery, normalized_name) DO UPDATE SET beer_id,
   brewery, name, created_at`. Пара, що вже вказувала на інший рядок, переходить на новий:
   найсвіжіше злиття має найсвіжіший доказ.
3. **Аліаси рядка, що зливається, не переносяться** — їх забирає `ON DELETE CASCADE`.
   - Серверний крон (`enrichOneOrphan`) і пошуковий шлях `/enrich/result` збагачують лише
     сироти, а сирота аліасів не має. Рядок з аліасами (злінкований) потрапляє в злиття **лише**
     через репарацію #384: крамниця опублікувала bid, що суперечить його `untappd_id`.
   - Аліаси доводили **старий** bid цього рядка. Перенести їх на власника нового bid означало б
     стверджувати ідентичність, якої ніхто не доводив.

`mergeIntoCanonical` уже бампає версію каталогу, тож окремий бамп не потрібен.

### Зміна `untappd_id` рядка відкидає його аліаси

Аліас доводить «пара = пиво з bid X». Коли в рядка змінюється bid, аліаси втрачають доказ.
Такий запис є рівно в двох місцях:

- **`recordLookupSuccess`** — репарація #384 переписує bid злінкованого рядка на новий
  (власника в нового bid ще немає). Перед `UPDATE` видаляються аліаси цього рядка, якщо його
  `untappd_id` не `NULL` і відрізняється від нового. Для сироти (`untappd_id IS NULL`) нічого
  не відбувається. Якщо `UPDATE` падає на `UNIQUE` (власник є), рядок далі зливається — і його
  аліаси все одно зникають каскадом.
- **`pinMatch`, гілка «новий bid»** (`pin-match.ts`) — людина пінить рядок на інший bid. Те саме
  правило: аліаси рядка, чий bid змінюється, видаляються.

`upsertBeerByBid` резолвить лише сироти, тож туди правило не потрібне.

## Читання: аліас перед матчером

### Завантаження (`loadAliases`)

```sql
SELECT a.beer_id, a.name, a.normalized_brewery, a.normalized_name
  FROM beer_aliases a JOIN beers b ON b.id = a.beer_id
 WHERE b.untappd_id IS NOT NULL
   AND NOT EXISTS (
     SELECT 1 FROM beers x
      WHERE x.normalized_brewery = a.normalized_brewery
        AND x.normalized_name    = a.normalized_name
        AND x.id <> a.beer_id)
 ORDER BY a.id
```

- **Жива перевірка лінку.** Аліас на рядок без `untappd_id` не читається — та сама перевірка,
  що й `isRememberedMerge` (#366).
- **Рядок каталогу важить більше за аліас.** Якщо після запису аліасу з'явився рядок `beers` з
  тією самою парою (сирота кранів; сирота, яку репарація #384 перетворила на рядок нового bid),
  аліас не читається, і картку відповідає матчер. Це те саме правило, що й під час запису, лише
  перевірене на момент читання; запит іде по наявному індексу `idx_beers_norm`.

### Індекс у кеші каталогу

`createCatalogCache` поруч із `prepared` і `byId` будує `aliases: AliasIndex` — мапу
«нормалізована пара → `{beerId, name}`». Каталог матчера (`prepared`) аліасів **не містить**:
- матчер не бачить дублікатів `id`;
- пул неточного пошуку для броварні не звужується аліасом (рев'ю, пункт 3);
- `byId` лишається з рядків `beers`, як і було.

`/match` і MCP (`match-tool.ts`) ділять один `CatalogCache` з композиційного кореня; обидва
передають `aliases` у `matchBeerList`.

### `matchBeerList`

Для кожної картки, **до** `matchPrepared`:

1. ключ = `normalizeBrewery(brewery)` + `normalizeName(name)`;
2. в індексі є аліас із цим ключем, **і** `numericTokensCompatible(назва картки, назва аліасу)`,
   **і** `byId` має його `beerId` → результат `exact` на цей рядок: `is_drunk`, `user_rating`,
   `searched: true`; матчер і бюджет повнокаталожного фолбеку не чіпаються;
3. інакше — матчер, як сьогодні.

**Правило цифр** (`numericTokensCompatible`, #617): нечислова частина назви рівна за ключем, а
числові токени мусять збігатися як мультимножина; рік порівнюється лише коли він є в обох.
- `ROCH / Trappistes Rochefort 10` проти аліасу `… Rochefort 8` → несумісні → матчер.
- `ROCH / Trappistes Rochefort 10` проти аліасу `… Rochefort` (без цифр) → несумісні → матчер.
- `X / Mjød` проти аліасу `X / Mjød 2021` → сумісні (рік є лише в одному) → аліас.

## `/enrich/*` (периферія)

### `ensureBeerRow`

Порядок: рядок `beers` з парою → **аліас з парою і сумісними цифрами** → нова сирота.
- **Влучання в аліас** повертає канонічний рядок і позначку `viaAlias: true`. Сирота не
  створюється.
- **Факти картки** (`fillOrphanFacts`) на аліасному влучанні **не пишуться**.

### `/enrich/candidates`

Для `viaAlias` рядок злінкований, тож без bid він не eligible, і пошуку немає.

### Репарація #384 через аліас

**Небезпека.** Сьогоднішній шлях `mayOverride` переписав би `untappd_id` **спільного**
канонічного рядка, хоча доказ стосується лише пари однієї картки.

**Правило: суперечливий bid на аліасі стосується лише аліасу.**

- **`/enrich/candidates`.** Для `viaAlias` і `contradicts` рядок **eligible** незалежно від
  `refusesBidOverride(untappd_id_source)`. `isNotABeer` і `isEligible` лишаються як є.
- **`/enrich/result`.** Для `viaAlias` і `bid !== stored`:
  1. `resolveByBid` з тими самими аргументами, що й сьогодні.
  2. **Прийнято:** в одній транзакції видалити аліас пари → `ensureOrphan` з парою картки →
     `applyLookupOutcome` на цій сироті. Bid нічий → сирота стає рядком цього bid; bid чийсь →
     злиття пише свіжий аліас. Далі `stampBidProvenance` і відповідь `matched`.
  3. **Відхилено:** аліас не змінюється, відповідь — збережений лінк канонічного рядка.
- **`viaAlias` і `bid === stored`** або без bid: відповідь `matched` зі збереженим лінком.

## Заявка → доказ

| Що записується або читається як факт | Що це доводить | Сила |
|---|---|---|
| Аліас «пара картки = рядок Z» після злиття за опублікованим bid | магазин опублікував bid, гейт броварні `resolveByBid` його прийняв | сильна |
| Той самий аліас після пошукового злиття | конвеєр `lookupBeer` зматчив саме цю пару. Ту саму заявку сирота мала б без конфлікту `UNIQUE`, і `/match` сьогодні читає її як `exact` | як у звичайного лінку |
| Аліас після злиття з крону (текст крана) | те саме, що й посилання крана з `confidence 1.0` (#366) | як у звичайного лінку |
| «Пара аліасу не належить жодному іншому рядку» | перевіряється в транзакції злиття **і** під час кожного читання | доведено на момент використання |
| «Аліас стосується картки з іншими цифрами в назві» | **нічого не доводить**: злиття бачило лише одну назву. Реплей рев'ю: без правила цифр `ROCH / Trappistes Rochefort 10` після злиття картки «…8» дає рядок 8 `exact` ✅ | заборонено правилом цифр |
| «Аліас доводить рядок після зміни його bid» | **нічого не доводить**: аліас записано під старим bid | аліаси відкидаються (`recordLookupSuccess`, `pinMatch`, каскад злиття) |
| «Аліас не перекриється пізнішою сиротою з тією самою парою» | проба 2026-09-14: 0 з 272 пар розширення збігаються з 1 491 нормалізованою парою кранів. Якщо все ж перекриється — рядок важить більше, аліас не читається, картка йде в матчер | **виміряне прийняте обмеження** |
| Аліас після репарації #384 (периферія) | прийнятий bid для цієї пари; старий аліас видаляється в тій самій транзакції | сильна |

**Обмеження.**
- Сирота кранів з точно тією самою нормалізованою парою вимикає аліас (рядок важить більше), і
  картка знову стає ⚪, доки злиття сироти не прибере рядок. Перевірку аліасу в `ensureOrphan`
  свідомо не додано: це змінило б поведінку кранів, а вона належить #632.
- Картка, яка має аліас на випите пиво Z, але крамниця публікує суперечливий bid, у клієнті
  **не** йде в дошук: `content/index.ts` не шле випите пиво на enrich (свідома обережність #384).
  Вона й далі показує Z з ✅, доки аліас не скасують.

## Скасування хибного аліасу

```
sudo -u warsaw-beer-bot bash -lc "sqlite3 /var/lib/warsaw-beer-bot/bot.db \
  \"DELETE FROM beer_aliases WHERE normalized_brewery = '<…>' AND normalized_name = '<…>'\""
```

- **Після скасування** наступне завантаження картки знову пройде петлю один раз. Якщо злиття
  знову поставить той самий аліас, дефект у доказі (bid крамниці чи пошук), а не в пам'яті.
- **Інструмента немає** (YAGNI), рецепт іде в `spec.md` поруч із `merged_at = NULL`.
- **`pinMatch`** зі зміною bid відкидає аліаси рядка сам (див. «Запис»).

## Тести

Кожен тест доводиться мутацією: видалити рядок коду → тест падає. Сіди мають видимі значення, а
не `null` (`feedback_stub_defaults_hide_mutations`).

**Storage (`beers.test.ts`, `pin-match.test.ts`)**
- Злиття пише аліас із сирою й нормалізованою парою сироти та `created_at`.
- Пара, яку має інший рядок `beers` (вінтажний близнюк), аліасом **не** стає.
- Конфлікт пари переписує `beer_id` на новий рядок.
- Злиття злінкованого рядка з аліасами **не** переносить їх на власника bid.
- `recordLookupSuccess` з іншим bid на злінкованому рядку видаляє його аліаси; з тим самим bid —
  лишає.
- `pinMatch` з новим bid на рядку з аліасами видаляє їх.
- `loadAliases`: не читає аліас рядка без `untappd_id` і аліас, чию пару тримає рядок `beers`.

**Домен (`match-list.test.ts`, `catalog-cache.test.ts`)**
- Аліасне влучання → `exact`, `is_drunk`, `user_rating`, канонічні назва й рейтинг,
  бюджет фолбеку не витрачено.
- Картка з несумісними цифрами (`8` проти `10`, без цифр проти `10`) аліасом **не** влучає.
- Кеш будує `aliases` з `loadAliases`, а `prepared` аліасів не містить.
- Інтеграційний: злиття на справжній БД → кеш → `matchBeerList` дає `exact` ✅; близнюк «…10» —
  ні.

**Підключення (`match.test.ts`, `mcp.test.ts`)**
- `POST /match` і MCP `match_beers` після злиття дають точний збіг зі статусом «пив» для картки
  крамниці. Без передачі `aliases` у `matchBeerList` тест падає.

**`/enrich/*` (периферія, `enrich.test.ts`)**
- Картка з аліасом → канонічний рядок, нова сирота не створюється, `eligible: false`.
- Картка з аліасом і суперечливим bid → `eligible: true`, навіть коли канонічний рядок
  `checkin`/`curated`.
- `/enrich/result`, bid прийнято: старий аліас видалено; новий аліас дивиться на рядок з bid;
  `untappd_id` і `untappd_id_source` канонічного рядка **не змінилися**.
- `/enrich/result`, bid відхилено: аліас і канонічний рядок без змін.

**Наскрізний тест петлі (API, периферія)**
- `/enrich/candidates` → `/enrich/result` з bid → злиття → `POST /match` з токеном дає `exact`,
  `is_drunk: true`, `user_rating`. На поточному `main` тест мусить падати.

**Міграція.** v32 на свіжій БД і на копії прод-БД без помилок. Таблиця порожня, наявні дані не
змінюються.

## Рев'ю ядра (2026-09-14)

Перша версія ядра (коміти `9325d68`, `67bacfe`) додавала аліаси **записами в каталог матчера** і
**переносила** аліаси рядка, що зливається. Наскрізне рев'ю знайшло, а контролер підтвердив:

1. **Числові близнюки — хибний ✅.** Нормалізація відкидає цифри, тож аліас картки «…8» ставав
   точним кандидатом і для картки «…10» з тієї самої етикетки. Реплей: `ROCH / Trappistes
   Rochefort 10` → рядок 8, `exact`, ✅, оцінка 4 (без аліасу — `fuzzy`, без ✅). Перевірка
   `claimed` під час запису ловить лише близнюка, що вже є рядком `beers`, а не картку.
   → Аліас винесено з каталогу матчера в окрему перевірку з правилом цифр.
2. **Аліаси йшли за рядком, чий bid переписано.** Рядок з аліасами досяжний для злиття чи
   перезапису bid лише через репарацію #384, тобто рівно тоді, коли аліаси втратили доказ.
   → Перенесення прибрано; зміна bid відкидає аліаси.
3. **Аліас звужував неточний пошук** для всієї своєї етикетки (пул броварні більше не порожній,
   повнокаталожний фолбек не запускається). → Зникає разом з п. 1.
4. **Три інші шляхи видалення рядків** (`dedupe-brewery-aliases`, `cleanup-polluted-ontap`,
   `pin-match`) — не блокер: перші два видаляють лише рядки без `untappd_id`, які не бувають
   ціллю аліасу; `pin-match` лише губить пам'ять, що з урахуванням п. 2 правильно.
5. **«Мертвий» аліас** після того, як репарація зробила сироту рядком нового bid. → Закрито
   правилом «рядок важить більше за аліас» під час читання.
