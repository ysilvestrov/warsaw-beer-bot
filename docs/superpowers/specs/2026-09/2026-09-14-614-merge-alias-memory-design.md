# Дизайн — пам'ять злиття для назв з крамниць: `/match` впізнає картку після першого пошуку (закриває #614)

**Дата:** 2026-09-14
**Issue:** [#614](https://github.com/ysilvestrov/warsaw-beer-bot/issues/614). Бід-резолв → злиття → `/match` знову
`null`: ті самі пива шукаються в сесії Untappd на кожному завантаженні, а бейдж після пошуку не
показує статусу «пив».
**Пов'язані:**
- #366 — пам'ять злиття для кранів, `match_links.merged_at`;
- #384 — ідентичність за опублікованим bid;
- #632 — петля злиттів на шляху кранів, виділено;
- #633 — `/match` приймає опублікований bid, виділено;
- #618 — назва Untappd окремо від ключа матчингу.

## Проблема (доведена)

### Петля

Назва картки в крамниці часто не збігається з назвою рядка в каталозі. Тоді на **кожне**
завантаження сторінки:

1. `POST /match` повертає `matched_beer: null`, і картка стає сиротою.
2. `/enrich/candidates` → `ensureBeerRow` створює **новий** рядок-сироту з парою картки
   (`untappd_lookup_count = 0`, тобто `eligible: true`).
3. Розширення шукає пиво в сесії Untappd користувача. Далі `/enrich/result`: bid крамниці
   приймається (`resolveByBid`) або його знаходить пошук. Bid уже належить іншому рядку, тож
   спрацьовує `SQLITE_CONSTRAINT_UNIQUE` → `mergeIntoCanonical` → сироту **видалено**.
4. Клієнт малює ⭐ (`setEnriched`) і нічого не кешує. Сервер теж нічого не запам'ятовує для
   `/match`: `merged_at` (#366) живе лише на `match_links`, а їх читає тільки інжест кранів.

Після кроку 4 стан такий самий, як до кроку 1. Бекоф петлю не зупиняє, бо щоразу рахує
новий рядок.

### Статус «пив» губиться

Відповідь `/enrich/result` — це `{status, untappd_id, rating_global}`. `setEnriched` малює ⭐
лише з цих полів. Навіть коли пошук правильно знаходить випите пиво, бейдж не показує ні ✅,
ні особистої оцінки. Такі поля за побудовою є лише у відповіді `/match`.

## Рішення

Злиття запам'ятовує пару «броварня + назва» сироти як **аліас** канонічного рядка. `/match`, MCP
і `/enrich/*` читають аліаси, тож друге завантаження тієї самої картки дає точний збіг з
особистим статусом. Пошук, створення рядка й злиття більше не повторюються. Зміна лише
серверна: розширення не змінюється, ефект настає після деплою.

**Рівень доказу — ✅ для обох шляхів злиття** (рішення користувача, 2026-09-14).
- **Злиття за опублікованим bid:** магазин опублікував bid, гейт броварні його прийняв. Це
  сильніше за збіг назв.
- **Злиття з пошуку:** якби bid не належав уже іншому рядку, сирота з цією самою парою просто
  отримала б `untappd_id`, і `/match` сьогодні читав би її як `exact`.

Злиття не повинно робити відповідь слабшою, ніж без нього.

### Поза скоупом

- **#632** — петля злиттів на шляху кранів. Спільний `ontap_ref` скидає `merged_at`, механізм
  інший. Цей дизайн не змінює `refresh-ontap` і `ensureOrphan`.
- **#633** — bid у `/match`: точний бейдж без жодного пошуку. Потрібен реліз розширення.
- **#618** — назва Untappd як аліас. Таблиця з цього дизайну може прийняти й таке джерело,
  але тут його немає (YAGNI).
- **Суфікс `IS` у назвах Flasker.** Фікс парсера закрив би лише такі картки. Red Mexican
  ламається без жодного суфікса.

## Дані: таблиця `beer_aliases` (міграція v32)

```sql
CREATE TABLE beer_aliases (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  beer_id            INTEGER NOT NULL REFERENCES beers(id) ON DELETE CASCADE,
  brewery            TEXT NOT NULL,   -- як надіслала картка (сирий текст)
  name               TEXT NOT NULL,
  normalized_brewery TEXT NOT NULL,
  normalized_name    TEXT NOT NULL,
  created_at         TEXT NOT NULL,
  UNIQUE (normalized_brewery, normalized_name)
);
CREATE INDEX idx_beer_aliases_beer ON beer_aliases(beer_id);
```

- **Сирі `brewery`/`name` зберігаються** для матчера. `prepareBeer` рахує `nameKeys` і
  `breweryAliases` із сирого тексту, а `extractYear` читає рік із сирої назви.
- **Нормалізовані колонки** потрібні для унікальності й для пошуку в `ensureBeerRow`. Там
  використовуються ті самі `normalizeBrewery`/`normalizeName`, що й `findBeerByNormalized`.
- **Бекфілу немає.** Сирота видаляється при злитті, тож відновлювати пару нема з чого. Таблиця
  заповнюється сама, щойно сторінку завантажать наступного разу (так само, як `merged_at`, #366).

## Запис: `mergeIntoCanonical`

У тій самій транзакції, **до** `DELETE FROM beers`:

1. **Аліаси сироти переходять** на канонічний рядок:
   `UPDATE beer_aliases SET beer_id = :canonical WHERE beer_id = :orphan`. Без цього каскадне
   видалення знищило б пам'ять, коли зливають рядок, який сам уже був ціллю аліасів.
2. **Пара сироти стає аліасом**, але лише коли **жоден інший рядок `beers`** (крім сироти) не
   має цієї нормалізованої пари.
   - Причина: ontap-сирота буває вінтажним близнюком злінкованого рядка. `normalizeName`
     відкидає числові токени, тож «Rochefort 8» і «Rochefort 10» мають одну пару. Аліас на
     таку пару дав би `/match` для «Rochefort 8» другого точного кандидата з `id` іншого вінтажу.
   - Для сироти з enrich-роуту умова виконується завжди: `ensureBeerRow` знайшов би наявний
     рядок з цією парою і не створив би сироту.
3. **Запис:** `INSERT … ON CONFLICT(normalized_brewery, normalized_name) DO UPDATE SET beer_id,
   brewery, name, created_at`. Пара, що вже вказувала на інший рядок, переходить на новий:
   найсвіжіше злиття має найсвіжіший доказ. Досяжно лише зі шляху кранів або з репарації нижче,
   бо enrich-роут на пару з аліасом сироту не створює.

`mergeIntoCanonical` уже бампає версію каталогу, тож окремий бамп не потрібен.

Запис стоїть у `mergeIntoCanonical`, а не в `applyLookupOutcome`. Це єдина точка, де сирота
зникає. Злиття за bid, з пошуку й з крону проходять через неї, тож жоден шлях не губить пам'ять.

## Читання

### Кеш каталогу (`/match` і MCP)

- **Що завантажується.** `loadCatalog` лишається як є. Кеш каталогу додатково завантажує
  аліаси, приєднані до канонічного рядка:

  ```sql
  SELECT a.beer_id AS id, a.brewery, a.name, b.abv, b.rating_global, b.untappd_id
    FROM beer_aliases a JOIN beers b ON b.id = a.beer_id
   WHERE b.untappd_id IS NOT NULL
  ```

- **Жива перевірка.** Аліас на рядок без `untappd_id` не завантажується — та сама перевірка, що
  й `isRememberedMerge` (#366). Досяжно, якщо канонічний рядок колись втратить лінк.
- **ABV береться з канонічного рядка.** Точна стадія спершу обирає за ABV
  (`ABV_TOLERANCE`). Аліас без ABV програв би іншому точному кандидату з ABV.
- **Підготовка.** `prepare` отримує `[...рядки, ...аліаси]`, а `byId` будується **лише з рядків
  `beers`**. Інакше аліас з тим самим `id` переписав би в `byId` канонічну назву назвою
  крамниці.
- **Результат.** Точний збіг на аліас дає `m.id` канонічного рядка, `drunkSet.has(id)` і
  `ratingByBeerId.get(id)`. Персональні поля працюють без змін у `match-list.ts`.

`/match` і MCP (`match-tool.ts`) ділять один `CatalogCache` з композиційного кореня, тож
отримують зміну разом.

### `ensureBeerRow` (`/enrich/candidates`, `/enrich/result`)

Порядок: рядок `beers` з парою → **аліас з парою** → нова сирота.
- **Влучання в аліас** повертає канонічний рядок і позначку `viaAlias: true`. Сирота не
  створюється.
- **Факти картки** (`fillOrphanFacts`) на аліасному влучанні **не пишуться**. Канонічний рядок
  злінкований, його факти прийшли з Untappd.

### `/enrich/candidates`

Для `viaAlias` рядок злінкований, тож без bid він не eligible, і пошуку немає.

### Репарація #384 через аліас

**Небезпека.** Магазин може опублікувати для картки з аліасом bid, що суперечить канонічному
рядку. Сьогоднішній шлях `mayOverride` переписав би `untappd_id` **спільного** канонічного
рядка. Від цього зламалися б його крани, чекіни й картки інших магазинів, хоча доказ стосується
лише пари однієї картки.

**Правило: суперечливий bid на аліасі стосується лише аліасу.**

- **`/enrich/candidates`.** Для `viaAlias` і `contradicts` рядок **eligible** незалежно від
  `refusesBidOverride(untappd_id_source)`, бо канонічний рядок не зачіпається. `isNotABeer` і
  `isEligible` (бекоф) лишаються як є.
- **`/enrich/result`.** Для `viaAlias` і `bid !== stored`:
  1. `resolveByBid` з тими самими аргументами, що й сьогодні.
  2. **Прийнято:** в одній транзакції видалити аліас пари → `ensureOrphan` з парою картки →
     `applyLookupOutcome` на цій сироті з резольвленим результатом.
     - Bid ще нічий → сирота стає рядком цього bid.
     - Bid чийсь → злиття, і `mergeIntoCanonical` пише свіжий аліас на рядок цього bid.
     - Далі `stampBidProvenance` і відповідь `matched`, як сьогодні.
  3. **Відхилено:** аліас не змінюється, відповідь — збережений лінк канонічного рядка. У
     пошуковий конвеєр аліасна картка не йде ніколи, так само як злінкований рядок сьогодні.
- **`viaAlias` і `bid === stored`** або без bid: відповідь `matched` зі збереженим лінком, як
  для будь-якого злінкованого рядка.

## Заявка → доказ

| Що записується як факт | Що це доводить | Сила |
|---|---|---|
| Аліас «пара картки = рядок Z» після злиття за опублікованим bid | магазин опублікував bid, гейт броварні `resolveByBid` його прийняв | сильна |
| Той самий аліас після пошукового злиття | конвеєр `lookupBeer` зматчив саме цю пару. Ту саму заявку сирота мала б без конфлікту `UNIQUE`, і `/match` сьогодні читає її як `exact` | як у звичайного лінку |
| Аліас після злиття з крону (текст крана) | те саме, що й посилання крана з `confidence 1.0` (#366) | як у звичайного лінку |
| «Пара аліасу не належить жодному іншому рядку» | перевіряється в транзакції злиття | доведено на момент запису |
| «Аліас не перекриється пізнішою сиротою з тією самою парою» | проба 2026-09-14: 0 з 272 пар розширення (`enrich_failures.source_url <> ''`) збігаються з 1 491 нормалізованою парою кранів (`resolveTapIdentity`). У ширшій вибірці 9 з 1 627 збігів, і всі 9 — рядки самих кранів (формат броварні `… Brewery`) | **виміряне прийняте обмеження** |
| Аліас після репарації #384 | прийнятий bid для цієї пари; старий аліас видаляється в тій самій транзакції | сильна |

**Обмеження.** Якщо `refresh-ontap` створить сироту з точно тією самою нормалізованою парою,
точна стадія обере новіший `id`, і картка знову стане ⚪. Відновиться вона наступним злиттям,
яке перепише аліас. Перевірку аліасу в `ensureOrphan` свідомо не додано: це змінило б
поведінку кранів, а вона належить #632.

## Скасування хибного аліасу

```
sudo -u warsaw-beer-bot bash -lc "sqlite3 /var/lib/warsaw-beer-bot/bot.db \
  \"DELETE FROM beer_aliases WHERE normalized_brewery = '<…>' AND normalized_name = '<…>'\""
```

- **Після скасування** наступне завантаження картки знову пройде петлю один раз. Якщо злиття
  знову поставить той самий аліас, дефект у доказі (bid крамниці чи пошук), а не в пам'яті.
- **Інструмента немає** (YAGNI), рецепт іде в `spec.md` поруч із `merged_at = NULL`.
- **Реліз не потрібен.** `pin-match` аліасів не торкається: піни стосуються кранів.

## Тести

Кожен тест доводиться мутацією: видалити рядок коду → тест падає. Сіди мають видимі значення, а
не `null` (`feedback_stub_defaults_hide_mutations`).

**Storage (`beers.test.ts`)**
- Злиття пише аліас із сирою й нормалізованою парою сироти та `created_at`.
- Аліаси сироти переходять на канонічний рядок і не зникають після каскадного видалення.
- Пара, яку має інший рядок `beers` (вінтажний близнюк), аліасом **не** стає.
- Конфлікт пари переписує `beer_id` на новий рядок.

**Кеш каталогу (`catalog-cache.test.ts`)**
- Аліас потрапляє в `prepared` з `id` і ABV канонічного рядка.
- `byId` містить лише рядки `beers`: `byId.get(id).name` — канонічна назва.
- Аліас на рядок без `untappd_id` не завантажується.

**`/enrich/*` (`enrich.test.ts`)**
- Картка з аліасом → канонічний рядок, нова сирота не створюється, `eligible: false`.
- Картка з аліасом і суперечливим bid → `eligible: true`, навіть коли канонічний рядок
  `checkin`/`curated`.
- `/enrich/result`, bid прийнято:
  - старий аліас видалено;
  - новий аліас дивиться на рядок з bid;
  - `untappd_id` і `untappd_id_source` канонічного рядка **не змінилися**.
- `/enrich/result`, bid відхилено: аліас і канонічний рядок без змін, відповідь — збережений лінк.

**Наскрізний тест петлі (API)**
- Сценарій: картка з назвою, відмінною від канонічного рядка з чекіном. `/enrich/candidates` →
  `/enrich/result` з bid → злиття.
- Очікування: `POST /match` з токеном дає `exact`, `is_drunk: true`, `user_rating`.
- **На поточному `main` тест мусить падати.** Це доказ, що він ловить петлю, а не випадково
  проходить.

**Міграція.** v32 на свіжій БД і на копії прод-БД без помилок. Таблиця порожня, наявні дані не
змінюються.

## Спостереження після деплою (чекпойнт)

- **Журнал:** на шляху розширення кожен bid зливається **щонайбільше один раз**.

  ```
  journalctl -u warsaw-beer-bot --since "<deploy>" -o cat \
    | grep -E 'identity from shop-published bid|merged duplicate orphan'
  ```

  Сьогодні 5120103 і 5794217 зливаються по 7 разів.
- **БД:** `SELECT count(*) FROM beer_aliases` росте, а кількість повторних злиттів падає.
- **Реплей `/match`** для `VARVAR / BLACK BEAN IS` після першого завантаження сторінки
  Flasker дає 2815 `exact` ✅ 4.5.
- **Регресія:** злиття зникли, а картки лишились ⚪. Значить, аліаси пишуться, але не
  читаються.

  - §5.2 — інваріант: «ідентичність, здобута злиттям, переживає повторну картку крамниці;
    суперечливий bid на аліасі переписує аліас, а не канонічний рядок».
- **Розширення не змінюється:** `docs/extension-install-uk.md` і `extension/CHANGELOG.md` не
  зачіпаються.

## Стадії

1. **Ядро:**
   - міграція v32;
   - запис у `mergeIntoCanonical`;
   - читання в кеші каталогу.

   На ньому петля вже закривається: після першого пошуку `/match` дає ✅. Потім наскрізне рев'ю.

   **Ядро безпечне для деплою окремо.** Без аліасної гілки `ensureBeerRow` картка з аліасом і
   суперечливим bid (`bidContradicts` у клієнті) створює звичайну сироту. Злиття в рядок цього
   bid переписує аліас (`ON CONFLICT`), а канонічний рядок не зачіпається. Периферія додає лише
   одне: відхилений bid більше не лишає поруч з аліасом сироту з тією самою парою, яка
   перекрила б його новішим `id`.
2. **Периферія, окремим планом після рев'ю ядра:**
   - аліасне влучання в `ensureBeerRow`;
   - репарація #384 через аліас;
   - наскрізний API-тест;
   - `spec.md`.
