# Скарги на помилки через бот: `/report` → дедуп проти GitHub issues → лінк або новий issue

Date: 2026-09-26
Status: proposed for review
Origin: brainstorming 2026-09-26; супутнє issue #713 (версія розширення на токен)

## Проблема і межа

Користувач, який бачить помилку в боті чи в розширенні, не має каналу, щоб про неї сказати:
GitHub вимагає акаунта й знання, як писати issue. Ця зміна додає в бот команду `/report`.
Вона збирає структуровану скаргу (джерело, категорія, опис, до 3 скріншотів чи відео) і
віддає її агенту. Агент або знаходить наявний issue (відкритий чи закритий) і дає на нього
лінк, або створює новий із правильними лейблами. Публікація **автоматична**, без людини між
скаргою й GitHub.

Поза межею (свідомо):

- **Побажання й ідеї.** Лише помилки; `enhancement` через цей потік не приходить.
- **Вердикт «регресія».** Без версії розширення користувача (#713) модель не може
  відрізнити регресію від застарілого клієнта. На пробі `gpt-5.6-sol` кидав монетку між
  «регресія» і «закритий дублікат» для тієї самої скарги (9 з 24 збігів). Вердикт
  повертається разом з #713.
- **Перевідкриття закритих issues** агентом. Це вирішує людина з дайджесту.
- **Аналіз відео моделлю.** Відео зберігається для людей; модель бачить лише зображення.
- **Публічні вкладення.** Медіа ніколи не потрапляє на GitHub.

## Потік користувача

`/report` працює лише в приватному чаті з ботом. Кроки:

1. **Джерело**: інлайн-кнопки «Бот» / «Розширення».
2. **Категорія**: кнопки, що підходять обраному джерелу (таблиця нижче).
3. **Опис**: текст, щонайменше 10 символів після `trim`. Коротший текст бот відхиляє
   з поясненням, і крок лишається тим самим.
4. **Медіа (необов'язково)**: до 3 файлів. Приймаються фото, зображення, надіслане як
   документ (`image/*`), і відео до 20 МБ (межа завантаження Bot API). Кожен файл
   підтверджується «додано (n/3)». Кнопки: «Готово» / «Без медіа». Завеликі файли
   відхиляються з поясненням. Інші типи (стікери, аудіо, документи-не-зображення) бот
   пропускає далі без відповіді: документ-не-зображення мусить дійти до `/import`, а що саме
   приймається, крок медіа каже прямо. Уточнено 2026-09-27 на рев'ю обв'язки.
5. **Підтвердження**: підсумок і попередження: «Опис у переказі буде опубліковано
   публічно на GitHub. Скріншоти й відео публічними не будуть — їх бачать лише розробники
   на сервері. Не пишіть в описі особистих даних». Кнопки «Надіслати» / «Скасувати».
6. **Відповідь**: одразу «Прийнято, аналізую…». Коли воркер закінчить, те саме
   повідомлення **редагується** на результат (формулювання — у розділі «Вердикти»).

`/cancel` або «Скасувати» на будь-якому кроці видаляє чернетку. Чернетка без дій 30 хв
вважається мертвою: наступне повідомлення людини обробляється так, ніби чернетки немає,
а сама чернетка видаляється.

### Категорії

| Ключ | Текст для користувача (uk) | Бот | Розширення | Лейбл-підказка |
|---|---|---|---|---|
| `wrong_beer` | Не те пиво / чужий рейтинг | ✓ | ✓ | `matcher-bug` |
| `no_rating` | Пиво без рейтингу | ✓ | ✓ | `matcher-bug` |
| `had_status` | Неправильно «пив / не пив» | ✓ | ✓ | `bug` |
| `stale_data` | Застарілі або хибні дані паба / кранів / крамниці | ✓ | ✓ | `parser-bug` |
| `route` | Маршрут або карта | ✓ | — | `bug` |
| `no_badge` | Позначка не з'являється на сторінці крамниці | — | ✓ | `extension-bug` |
| `ext_broken` | Розширення не працює: вхід, встановлення, оновлення, меню | — | ✓ | `extension-bug` |
| `bot_broken` | Бот не відповідає, зависає або видає помилку | ✓ | — | `bug` |
| `text_ui` | Текст, переклад, оформлення | ✓ | ✓ | `bug` |
| `other` | Інше | ✓ | ✓ | `bug` |

Категорія — **підказка**, а не вердикт: вона йде в обидва кроки агента, але лейбли
остаточно обирає агент за змістом (правила — у розділі «Валідація»).

### Перехоплення апдейтів і порядок middleware

Middleware «активна чернетка» забирає апдейт **лише** тоді, коли в людини є жива
чернетка і тип апдейту відповідає кроку:

- текст — на кроці 3;
- фото, `image/*`-документ, відео — на кроці 4.

Усе інше проходить далі без змін. Зокрема, документ-CSV на кроці 4 не є `image/*`, тож
він дістається `/import`, як і сьогодні. Команди (`/…`) чернетка не забирає ніколи,
крім `/cancel`. Порядок реєстрації цього middleware відносно `importCommand` — інваріант
composition root: інтеграційний тест + source-guard.

Стан діалогу зберігається в БД, а не в пам'яті: деплой посеред дня не повинен губити
скаргу.

## Ліміти й захист

- **Хто може**: будь-хто з рядком у `user_profiles`, крім забанених.
- **На людину**: 3 надіслані скарги за варшавську добу, лічильник за `bug_reports.created_at`.
  Ліміт перевіряється двічі: на вході в `/report` (щоб людина не заповнювала форму даремно)
  і на кроці 5 (паралельні чернетки). Четверта скарга відхиляється з поясненням, LLM не
  викликається.
- **Глобальна стеля**: 20 **оброблених** скарг за варшавську добу, лічильник за
  `processed_at`. Скарга понад стелю лишається `queued`, а користувач бачить «прийнято,
  відповім пізніше». Наступного дня крон її підбере.
- **Подвійне «Надіслати» (з AI-рев'ю PR #715):** чернетка забирається синхронно до першого
  `await`, тож друге натискання бачить «неактуальна». Рядок скарги й медіа — одна транзакція.
  Прийнятий ризик: падіння під час скачування губить скаргу. Спроба це закрити (тримати
  чернетку до вставки) відкрила подвійні скарги, які трапляються значно частіше.
- **Ліміт і гонка (прийнятий ризик):** повторна перевірка ліміту при «Надіслати» не атомарна зі
  вставкою рядка, бо між ними скачується медіа (до 60 с на файл). Людина, яка встигне за цей час
  пройти ще один діалог до кінця, отримає четверту скаргу за добу. Шкоди від цього немає, тож
  ризик прийнято на рев'ю обв'язки 2026-09-27.
- **Бан**: перевіряється і на `/report`, і при «Надіслати» (бан, виданий посеред діалогу,
  діє одразу). Адмінська команда `/reportban <telegram_id>` вимикає скарги людині,
  `/reportban <telegram_id> off` вмикає знову. Працює лише для `ADMIN_TELEGRAM_ID`.
  Забанений бачить «скарги недоступні».
- **Сміття** (спам, питання, побажання) відсіює агент на кроці 2 вердиктом `not_a_bug`.
  Issue не створюється.

## Агент: два кроки

### Список кандидатів

Беруться всі issues, відкриті й закриті, що несуть **хоча б один** із лейблів
`bug`, `extension-bug`, `parser-bug`, `matcher-bug`. PR із відповіді `/issues`
відкидаються. Список кешується в пам'яті на 10 хв; створення issue цим потоком
кеш інвалідовує, щоб дві однакові скарги поспіль не створили два issues.

Виміряно 2026-09-26: 293 issues, з них 169 під фільтром (39 відкритих), ~27k символів,
~11k токенів у Jev.

Передумова розгортання: користувацькі баги без жодного з чотирьох лейблів (#609, #635,
#612 та інші) розмічаються разово: агент (antigravity) за окремим промптом додає один
з чотирьох лейблів кожному issue, чий симптом може побачити користувач, а людина
погоджує таблицю до застосування. Це операційний крок, коду не потребує.

### Крок 1 — відбір (`typesafe/jev-1.13`, OpenRouter Decisions API)

`POST https://openrouter.ai/api/alpha/decisions`:

- `state`: `{ source, category, report: <текст користувача> }`;
- одне питання `duplicate_of` типу `choice`, де `criteria` — це
  `i<N>: "#N [state] <лейбли без Severity/effort> — <заголовок>"` для кожного кандидата,
  плюс `none: "None of the listed issues describes this same problem."`.

З `probabilities` беруться 5 найімовірніших ключів. `none` серед них просто відкидається,
тобто кандидатів може бути менше 5, зокрема нуль. Зображень Jev не приймає (за
документацією API), тож цей крок працює лише з тексту.

Стеля контексту Jev — 32 000 токенів. Якщо оцінка розміру списку (символи / 2.5)
перевищує 28 000, список обрізається: спершу відкидаються найстаріші закриті issues.
Це пишеться в лог і в рядок скарги (`candidates_truncated = 1`).

### Крок 2 — вердикт (`gpt-5.6-luna`, OpenAI напряму)

Виклик іде на `https://api.openai.com/v1/chat/completions` нашим `OPENAI_API_KEY`. Форма тіла та сама, що в `scripts/ai-review/openai.ts`: `max_completion_tokens` + строга `json_schema`. Нове в ній лише `image_url` з `data:`-URL. Цю частину ще не пробували напряму: проби йшли через OpenRouter тим самим вендором, тож токени й ціна виміряні правильно, а сама форма запиту — ні. Тому перший крок задачі з клієнтом — один живий виклик зі скріншотом (передумова: ключ у прод-`.env`).

На вхід:

- скарга (джерело, категорія, текст);
- найсвіжіша опублікована версія розширення: `job_state['extension_announced_version']`, яку анонсер #379 бере з ендпойнта оновлень Chrome (`extension_releases` виведено з ужитку в #267, туди ніхто не пише з 2026-08-08; виправлено 2026-09-27), лише для джерела
  «Розширення»;
- кандидати: для кожного номер, стан, `closed_at`, `state_reason`, лейбли, тіло
  (перші 6 000 символів) і три останні коментарі (по 1 500 символів);
- до 3 зображень як `data:`-URL.

Вихід — строга JSON-схема:

| Поле | Тип / ліміт |
|---|---|
| `verdict` | `new` \| `duplicate_open` \| `duplicate_closed` \| `not_a_bug` |
| `issue_number` | ціле або `null` |
| `title` | ≤ 100 |
| `summary` | ≤ 300 |
| `where` | ≤ 200 |
| `subjects` | ≤ 5 × 100 |
| `expected`, `actual` | ≤ 200 кожне |
| `steps` | ≤ 5 × 150 |
| `screen_evidence` | ≤ 5 × 150 |
| `new_evidence` | ≤ 300 |
| `labels` | підмножина `bug`, `extension-bug`, `parser-bug`, `matcher-bug` |
| `severity` | `Severity-1…4` |
| `effort` | `effort/S\|M\|L` |

Промпт (текст фіксується в плані):

- заповнювати поля українською;
- **жодних персональних даних** (імена, ніки, Untappd-юзернейми, email, телефони, id);
- **жодних дослівних цитат користувача**; дослівно лише текст продукту на екрані;
- **лише симптом**, без здогадок про причину;
- порожнє поле, коли даних немає;
- severity — за шкалою, викладеною в промпті стисло з `docs/issue-severity.md`.

### Валідація виходу кроку 2 (код, не довіра до моделі)

Вихід, що порушує будь-яке правило, вважається невалідним: один повтор виклику, далі
скарга йде в `failed`.

- `issue_number` ≠ `null` ⟺ `verdict ∈ {duplicate_open, duplicate_closed}`.
- `issue_number` мусить бути серед кандидатів кроку 1.
- `duplicate_open` вимагає, щоб кандидат був `open`, а `duplicate_closed` — щоб `closed`,
  за даними GitHub, а не моделі.
- Лейбли поза дозволеним набором відкидаються, а не валять вердикт.

Код сам доповнює лейбли нового issue:

- завжди `user-report`;
- `extension-bug`, якщо джерело «Розширення»;
- `bug`, якщо після фільтрації не лишилося жодного з чотирьох.

Рядки обрізаються до лімітів кодом (схема лише просить). Після цього редактор
(`bug-report-redact`) вирізає з усіх полів:

- `@нік`;
- email;
- телефони (послідовності з ≥ 9 цифр із роздільниками `+ ( ) - пробіл`);
- посилання `untappd.com/user/…`.

## Вердикти й запис у GitHub

| Вердикт | GitHub | Відповідь користувачу |
|---|---|---|
| `new` | Новий issue за шаблоном, лейбли + `Severity-N` + `effort/*` | «Створено issue #N» + лінк |
| `duplicate_open` | Коментар у #N за шаблоном; лейбли #N не чіпаються | «Вже відомо, відкрито: #N. Додали ваші дані» + лінк |
| `duplicate_closed`, `state_reason = completed` | Коментар у закритий #N; issue лишається закритим | «Це виправлено {closed_at}. Якщо бачите після оновлення — надішліть скаргу ще раз» + лінк |
| `duplicate_closed`, інший `state_reason` | Те саме | «Вже відомо: #N (закрито {closed_at})» + лінк |
| `not_a_bug` | Нічого | «Схоже, це не помилка бота чи розширення» |

### Шаблон issue

LLM не пише markdown. Тіло рендерить `bug-report-template` з полів:

```
## Симптом
{summary}

**Де:** {where}
**Об'єкти:** {subjects, через кому}
**Очікувано:** {expected}
**Фактично:** {actual}

## Кроки
1. {steps[0]}
…

## Видно на скріншотах
- {screen_evidence[0]}
…

## Контекст
| Джерело | Категорія | Версія розширення | Місто | Мова |
|---|---|---|---|---|
| … | … | невідома (остання опублікована: X.Y.Z) | … | … |

Severity і effort — оцінка агента.
Скарга R-{id} · медіа: {n} файл(и), лише на сервері: `bug-reports/{id}/`
<!-- bug-report:{id} -->
```

- Порожнє поле рендериться як «—».
- Розділи «Кроки» і «Видно на скріншотах» при порожньому масиві пропускаються цілком.
- Колонка «Версія розширення» для джерела «Бот» — «—».
- «Місто» береться з профілю, «Мова» — з локалі.
- Telegram-id, ніку чи імені в тілі **немає**.

Коментар до дубліката рендериться тим самим шаблоном без заголовка. Перед розділом
«Симптом» іде рядок `**Нове в цій скарзі:** {new_evidence}` (або «—»).

### Ідемпотентність

GitHub-запис і запис у БД не атомарні: між «issue створено» і «номер записано» процес може
впасти. Тому:

1. Перед будь-яким записом у GitHub статус стає `publishing` (окрема транзакція).
2. Після успіху за одну транзакцію пишуться `issue_number`, `verdict`, `processed_at`,
   статус `done`.
3. Скарга, знайдена в `publishing` на старті воркера, **не ретраїться автоматично**.
   Вона переходить у `needs_review`, потрапляє в дайджест, а користувач отримує
   «прийнято, розробник перевірить вручну».
4. Автоматично ретраяться лише збої **до** `publishing`: LLM, мережа, 5xx, 429
   (класифікатор — наявний `isTransient`). Максимум 3 спроби на скаргу (#316), далі
   `failed`: користувач отримує «не вдалося обробити, розробник подивиться», а скарга
   потрапляє в дайджест.
5. `not_a_bug` у GitHub нічого не пише, тож `publishing` для нього не ставиться.
6. **401, 402, 403 від будь-якого зовнішнього сервісу — це наш ключ, а не скарга**
   (відкликаний, скінчилися кредити, немає прав). Скарга лишається `queued`, спроба не
   рахується, прогін зупиняється з `log.error`. Інакше за один прогін уся черга стала б
   `failed`, і кожен користувач почув би «не вдалося». Реальний сценарій: ключ OpenRouter
   передплачений. Після `publishing` діє п. 3, бо запис міг відбутися. Додано 2026-09-27 на
   рев'ю воркера. Що саме стоїть, дайджест покаже в стадії обв'язки.

Редагування повідомлення користувачу — останній крок і best-effort. Якщо Telegram його
відкидає (повідомлення видалено, бот заблокований), це пишеться в лог і на статус не
впливає.

## Дані (міграція v38)

- **`bug_report_drafts`** — `telegram_id` PK, `step`, `source`, `category`, `text`,
  `media_json` (масив `{file_id, kind, file_size}`), `updated_at`.
- **`bug_reports`**:
  - `id` PK;
  - `telegram_id`, `chat_id`, `status_message_id`, `locale`, `city`;
  - `source`, `category`, `text`;
  - `status` ∈ (`queued`, `publishing`, `done`, `failed`, `needs_review`) — CHECK;
  - `attempts`, `last_error`, `candidates_truncated`;
  - `verdict`, `issue_number`;
  - `created_at`, `processed_at`.
- **`bug_report_media`** — `report_id` FK, `idx`, `kind` (`photo`\|`video`), `path`,
  `bytes`, `pruned_at`.
- **`bug_report_bans`** — `telegram_id` PK, `banned_at`.

`text` зберігається в БД дослівно: сервер приватний, а людині, що фіксить, першоджерело
потрібне. Публічним стає лише переказ.

### Медіа

- Скачується **на кроці 5, одразу після «Надіслати»**: посилання Telegram на файл живе
  годину, а обробка може бути завтра.
- Шлях: `{BUG_REPORT_MEDIA_DIR}/{id}/{idx}.{ext}`. Файл пишеться, робиться `fsync`, і лише
  тоді додається рядок у `bug_report_media`.
- Якщо скачати не вдалося, скарга все одно створюється, `bytes = 0`, а шаблон пише
  «медіа: не збережено».
- Прибирання: у наявному нічному кроні (03:00) файли скарг, старших за 180 днів,
  видаляються, а рядок отримує `pruned_at`.

## Воркер і розклад

- `jobs/bug-report-worker.ts` обробляє по одній скарзі з `queued`, від найстаріших.
- Re-entrancy guard, як в orphan-triage.
- Запускається одразу після «Надіслати» і кроном `*/15`: підбирає відкладені й ті, що
  впали з транзієнтною помилкою.
- Послідовність для однієї скарги:
  1. перевірка стелі;
  2. крок 1;
  3. крок 2 + валідація;
  4. `publishing` (якщо треба);
  5. GitHub;
  6. `done`;
  7. редагування повідомлення.

## Дайджест

Рядок у наявному щоденному дайджесті адміну:

> скарги за добу: оброблено N (нових M, відкритих дублікатів K, закритих дублікатів C,
> не-баг L), у черзі Q, потребують перевірки P, збоїв F

Під ним окремим списком — лінки на **всі прив'язки до закритих issues** за добу. Хибний
дублікат найдорожчий саме там: користувач чує «виправлено», а скарга тоне в закритому
issue. Далі — список `needs_review` і `failed` з `R-{id}`.

## Тести

- **Машина станів**: кожен перехід; кожен тип апдейту на кожному кроці (фото на кроці 3,
  текст на кроці 2, CSV-документ на кроці 4 → не забирається); 10 символів проти 9;
  4-й файл; відео 20 МБ проти 20 МБ + 1 байт; 30 хв проти 30 хв + 1 с; `/cancel`;
  ліміт на людину на 2/3/4; бан.
- **Валідатор**: дублікат поза кандидатами; `duplicate_open` на закритий issue;
  `new` з номером; `not_a_bug` з номером; чужий лейбл відкидається; доповнення лейблів
  для кожного джерела.
- **Редактор**: кожен шаблон окремо, а також числа, що **не** є телефоном (ABV `6.5`,
  рейтинг `4.12`, рік `2026`, bid `6172824` — 7 цифр).
- **Шаблон**: порожні поля, порожні масиви, обрізання на межі ліміту, джерело «Бот» проти
  «Розширення».
- **Воркер** зі стабами LLM і GitHub із видимими значеннями:
  - кожен вердикт;
  - транзієнтний збій → повтор; третій → `failed`;
  - скарга в `publishing` на старті → `needs_review` і **нуль** викликів `createIssue`;
  - стеля 19/20/21;
  - кеш інвалідовується після `new`;
  - `state_reason` → два тексти для закритого дубліката.
- **Кандидати**: PR відкидаються; фільтр лейблів; обрізання понад 28 000 із відкиданням
  найстаріших закритих.
- **Composition root**: інтеграційний тест «CSV під час активної чернетки доходить до
  `/import`» + source-guard порядку middleware.
