# План (ядро): спільне ядро синку й локальна база чекінів (#924)

Спека: `docs/superpowers/specs/2026-10/2026-10-31-924-local-checkin-db-design.md` (затверджено 31.10).

**Ядро** — механізм, на якому стоїть решта:
- `src/shared/` (парсер, запобіжники, покриття, висновок);
- перехід серверного роуту на нього;
- сховище IndexedDB і локальні `getState`/`submitPage` для `runCheckinSync`;
- `sessionUsername`.

**Обв'язка — окремим планом після наскрізного рев'ю ядра й після #934:** накладання ✅ (§5),
режим, popup, Options, документи й політика (§6–7), тести 6–7 спеки.

**Інваріант ядра.** Видима поведінка не змінюється:
- сервер відповідає байт-у-байт так само;
- розширення без Telegram-токена ще не викликає локальний синк, бо його ніщо не підключає до popup чи
  фонового скрипта.

Тому ядро можна мерджити окремо.

**Гейти:**
- root: `npm test && npm run typecheck`;
- розширення: `cd extension && npm test && npm run typecheck && npm run build`.

Тести — лише через `npm test -- <args>`. Обидва гейти ганяються у WSL-копії. Відомі збої середовища
root: `release`, `db-snapshot`, `trial-migrate`, іноді `install-image` і два таймаути.

**Незмінне — доказ.** `git diff origin/main -- src/api/routes/checkins.test.ts src/storage/checkin_coverage.test.ts`
порожній на кожному коміті. Якщо котрийсь із цих тестів довелося змінити, зупиняємось: змінилася
поведінка (спека §2).

## Задача 1 — `src/shared/`: перенесення парсера й межа пакета

Перенести файли (`git mv`):

| Звідки | Куди |
|---|---|
| `src/sources/untappd/checkin-feed.ts` | `src/shared/untappd/checkin-feed.ts` |
| `src/sources/untappd/block.ts` | `src/shared/untappd/block.ts` |
| `canonicalCheckinAt` з `src/storage/checkins.ts` | `src/shared/checkin-sync/checkin-at.ts` |

- На старих місцях — однорядкові реекспорти: `export * from '../../shared/untappd/checkin-feed';`
  тощо. У `checkins.ts` — `export { canonicalCheckinAt } from '../shared/checkin-sync/checkin-at';`,
  якщо вона експортована; якщо ні — import.
- Наявні тести парсера (`checkin-feed.test.ts`) і фікстури лишаються на місці, імпорт через
  реекспорт. Жоден споживач не змінюється.
- Новий `src/shared/boundary.test.ts`:
  - для кожного `.ts` у `src/shared/**` (крім `*.test.ts`) розбирає `import … from '…'`;
  - падає, якщо відносний шлях виходить за `src/shared/`;
  - падає, якщо голий модуль не входить у `['cheerio', 'domhandler']`;
  - падає на `node:*`.
  - Список дозволених модулів — константа в тесті. Поточні імпорти парсера (`cheerio`, тип
    `domhandler`) проходять.
- Перевірити, що `checkin-feed.ts` не тягне `Buffer`/`process`: це доведено пробою 1 спеки, а
  тест межі ловить `node:*`.

## Задача 2 — чисте покриття й паритет із SQL

`src/shared/checkin-sync/coverage.ts`:

```ts
export interface CoverageRange { from_id: number; to_id: number }
export function mergeRange(ranges: readonly CoverageRange[], from: number, to: number): CoverageRange[];
export function rangeContaining(ranges: readonly CoverageRange[], id: number): CoverageRange | null;
```

- `mergeRange` кидає `invalid coverage range` на тих самих входах, що `addCoverage`: нецілі числа
  або `from > to`.
- Зливає діапазони, що перетинають `[from-1, to+1]`. Повертає новий масив, відсортований за
  `from_id` спаданням, як `coverageFor`.
- `storage/checkin_coverage.ts` реекспортує `CoverageRange` звідси. SQL `addCoverage` не змінюється.

Тест `src/shared/checkin-sync/coverage.test.ts`:
- **граничні випадки:** дотик `200`/`201` дає злиття; розрив в один id лишає два діапазони;
  вкладений діапазон; поглинання трьох діапазонів; невалідні входи кидають.
- **паритет** (`coverage-parity.test.ts`, root): SQLite у пам'яті з поточною схемою.
  - Seeded PRNG генерує 500 послідовностей по 1–12 кроків, id з `[1, 400]`.
  - Після кожного кроку `coverageFor(db, …)` дорівнює `mergeRange`, накопиченому над масивом.
  - Очікуване значення не обчислюється повторенням логіки: це порівняння двох незалежних
    реалізацій, а граничні випадки вище фіксують сам факт.

## Задача 3 — `checkPage`, `conclude` і перехід роуту

`src/shared/checkin-sync/guards.ts`:
- `checkPage(page, maxId, oldestKnown): PageVerdict` з типом зі спеки §1.1;
- порядок і коди — дослівно з роуту: `cursor_format` → порожня сторінка (`empty_above_known` →
  `no_session` 422 або `empty`) → `oldest_above_cursor` → `page_contains_cursor`.

`src/shared/checkin-sync/conclude.ts`:
- `conclude({count, profileTotal, ranges, oldest})` → `{caughtUp, nextCursor}`;
- коментарі з роуту (`profile_total`, що зменшується; доведення спуску #854) переїжджають сюди.

`src/api/routes/checkins.ts`:
- `checkPage` замінює інлайн-перевірки, `conclude` замінює обчислення `caughtUp`/`nextCursor`;
- `refuse(...)` і поля логу (`reason`, `pageSize`, `hasCursor`) — ті самі;
- запис чекінів, `addCoverage`, `recordProfileTotal`, `isBlockPage` до парсингу — без змін.

`src/shared/checkin-sync/scenarios.ts` — таблиця сценаріїв, з якої тести беруть і вхід, і
очікування:
- кожен сценарій: стан до (чекіни, покриття, `profileTotal`) → сторінка (з фікстур) + `maxId` →
  очікувана відповідь (відмова з кодом або `{merged, alreadyKnown, nextCursor, serverCount}`) і
  покриття після;
- сценарії #587: порожня вище/нижче відомого, `oldest_above_cursor`, `page_contains_cursor`;
- сценарій #854: id вище курсора;
- `caughtUp` при `profileTotal`, що зменшився, з двома діапазонами → не `caughtUp`;
- звичайний крок униз.

Тести:
- `guards.test.ts` і `conclude.test.ts` — по одному тесту на кожну гілку;
- `src/api/routes/checkins.scenarios.test.ts` (новий) проганяє `scenarios` через справжній роут
  на SQLite у пам'яті. Старий `checkins.test.ts` не змінюється.

`spec.md`: у розділі синку чекінів — одне речення про те, що правила сторінки й висновку живуть у
`src/shared/checkin-sync/` і спільні з розширенням. Поведінка не змінюється.

## Задача 4 — підключення `src/shared/` до розширення

- `extension/package.json` devDependencies:
  - `cheerio` (та сама мажорна, що в корені);
  - `fake-indexeddb`.

  CI-нога розширення ставить лише `extension/node_modules`, тож корінь їй недоступний.
- `extension/vite.config.ts` і `vitest.config.ts`:
  `resolve.alias: { cheerio: <abs>/extension/node_modules/cheerio/slim }`. Абсолютний шлях
  потрібен, бо файл у `src/shared/` інакше шукав би `cheerio` у кореневих `node_modules`.
- `extension/tsconfig.json`:
  - `paths` для `cheerio` і `domhandler` на `extension/node_modules`;
  - `include` + `../src/shared`.

  Код у `src/shared/` мусить проходити обидва конфіги, зокрема `noUnusedLocals` розширення.
- `extension/src/shared/core-boundary.test.ts`: сканує `extension/src/**/*.ts` і падає на імпорті
  з кореня, що не веде в `src/shared/`.
- `extension/src/local/parser-parity.test.ts`:
  - парсить 4 фікстури з `src/sources/untappd/__fixtures__/` через `parseCheckinFeedPage`, яку
    вже резолвить alias, тобто `cheerio/slim`;
  - порівнює з еталонами `__fixtures__/*.expected.json`. Еталони генеруються **один раз** у
    корені повним `cheerio` і комітяться; генерацію робить окремий скрипт у тексті коміту, а не
    тест.
- `npm run build` розширення проходить. Розмір `dist/` до й після записується в опис коміту.
  Очікування: **+0**. У ядрі `background/index.ts` локальний синк ще не імпортує, тож парсер у бандл
  не потрапляє. +~200 KB (проба 3 спеки) з'являться в обв'язці, коли синк підключать.

## Задача 6 — сховище IndexedDB і локальний синк

`extension/src/local/db.ts` (спека §3):
- `openLocalDb()`;
- `readPageSnapshot(tx, ids)` → `{knownIds, oldestKnown, count, ranges, meta}`;
- `writePage(tx, …)`;
- `clearLocalDb(abort)`: обрив, `localDbGeneration++` у `chrome.storage.local`, `deleteDatabase`;
- `localGeneration()`.

Одна транзакція `readwrite` на `checkins`, `coverage`, `meta`. Між читанням і записом немає
`await` поза IDB.

`extension/src/local/sync.ts`:
- `localSyncDeps({ fetchHome, generation })`:
  - `getState` (§4.1): `fetch('https://untappd.com/')` → `sessionUsername`; власник; `linkRevision`
    = покоління;
  - `submitPage(html, maxId, linkRevision)` (§4.2):
    1. `isBlockPage`;
    2. парсинг;
    3. у транзакції — звірка покоління з `meta.generation` (`account_changed` без запису),
       `checkPage`, злиття чекінів з **заміною** `bid`/`user_rating`/`checkin_at` (і `null`), а також
       `canonicalCheckinAt`, `mergeRange`, `profileTotal`;
    4. `conclude`.
  - Помилки — `ApiError` з тими самими кодами, що в серверного клієнта.

`extension/src/background/handle-checkin-sync.ts`: на етапі `getState` зберігати `no_session` і
`account_changed` (спека §4.1).

Тести (`fake-indexeddb/auto` у тестовому файлі):
- сценарії `scenarios.ts` через локальний `submitPage` — ті самі очікування, що для роуту
  (тест 3 спеки);
- пізня сторінка після `clearLocalDb` → `account_changed`, обидві бази без запису (тест 10);
- рейтинг 4.5, потім та сама сторінка без рейтингу → `user_rating: null` (тест 11);
- `getState` з іншим іменем → `SyncOutcome.status === 'account_changed'`, без сесії →
  `'no_session'` (тест 12);
- `runCheckinSync` на 3 сторінки з локальними deps і `fetch`-моком: жодного запиту, URL якого
  починається з `baseUrl` (тест 8);
- `clearLocalDb` → три сховища порожні, `meta` немає, наступний `getState` створює нового власника
  з новим поколінням (тест 9).
