# Severity відкритих issues: як визначати

Лейбли `Severity-1` … `Severity-4` кажуть, **наскільки шкодить** дефект або
відсутність фічі. Вони **не** кажуть, скільки коштує фікс — це окремий лейбл
`effort/S|M|L`. Черговість роботи: найвища severity, а всередині неї —
найменший effort.

Шкода міряється проти двох цілей проєкту, і тільки проти них:

1. **Відповідь людині.** Бот допомагає обрати правильне пиво під запит:
   рейтинг, «пив / не пив», фільтри, маршрут.
2. **Гроші.** Хобі-проєкт із бюджетом **$20–40/міс** (інфраструктура, LLM,
   проксі, веб-пошук, експерименти; без вартості девелопменту).

## Шкала

`Severity-1` — найгірше.

| Рівень | Відповідь людині | Гроші |
|---|---|---|
| **Severity-1** | Основний сценарій зламаний для всіх або більшості: бот не відповідає, рекомендації порожні або масово хибні | Витрата без стелі (цикл, що може тривати необмежено) або ≥ $10/міс зайвого |
| **Severity-2** | **Хибна** відповідь для класу пив або користувачів: чужий рейтинг, «пив», коли не пив, чи навпаки; неправильний лінк на крані | $3–10/міс зайвого |
| **Severity-3** | **Відсутня** відповідь: пиво на крані без рейтингу (сирота), несвіжі дані, збій з обхідним шляхом | < $3/міс, або грошовий ризик, що ще не настав |
| **Severity-4** | Косметика, зручність, внутрішні інструменти без впливу на відповідь; сирітські патерни без живих рядків | Копійки |

## Модифікатори (застосовувати по порядку)

1. **Хибне гірше за відсутнє.** Сирота чесно каже «рейтингу не знаю»;
   хибний лінк упевнено радить не те. Хибний матч — на рівень вище за
   сироту з тим самим охопленням (саме тому вони в різних рядках шкали).
2. **Тиха поломка: +1 рівень** (до максимуму `Severity-1`). Якщо `/status`,
   дайджест чи будь-який індикатор показує ✅, поки щось не працює, поломка
   триває необмежено. Issue **про сам моніторинг**, що бреше, отримує
   `Severity-3`; `Severity-2` — лише якщо він прямо зараз ховає живу поломку,
   названу в issue або його коментарях.
3. **Охоплення — живі крани, а не рядки в БД.** Кількість рядків
   `enrich_failures` завищує роботу: більшість давно не на кранах. Для
   сирітських issue рахуй запитом нижче; `on_tap_now = 0` і
   `shop_seen_14d = 0` → `Severity-4`, скільки б рядків не було.
4. **Інструменти успадковують severity того, що захищають, максимум
   `Severity-3`.** Тріаж-агент (`triage-quality`), AI-рев'ю PR, autodeploy,
   CI, моніторинг. Винятки: інструмент сам палить гроші (тоді — грошова
   колонка шкали) або прямо зараз ховає живу поломку (модифікатор 2).
5. **Ризики масштабу — максимум `Severity-3`**, поки навантаження
   гіпотетичне (`scale/*`, rate limiting, ріст таблиць). Переоцінюються,
   коли реальний трафік до них наближається.
6. **Фіча, якої немає** (enhancement), оцінюється за тим, яку шкоду завдає
   її відсутність сьогодні. Побажання без названої шкоди — `Severity-4`.

## Effort

| Лейбл | Що означає |
|---|---|
| `effort/S` | Відомий корінь, фікс у 1–2 файлах, легкий шлях з `CLAUDE.md` або операційна дія (ре-арм, `UPDATE`, закриття) |
| `effort/M` | Корінь відомий, але потрібен повний цикл (спека → план → worktree) |
| `effort/L` | Корінь невідомий або потрібне нове поняття / дизайн на кілька стадій |

## Як міряти охоплення сирітського issue

Прод-БД читається тільки в режимі `ro`:

```bash
sqlite3 -header -column 'file:/var/lib/warsaw-beer-bot/bot.db?mode=ro' "
WITH latest AS (
  SELECT pub_id, MAX(snapshot_at) AS s FROM tap_snapshots GROUP BY pub_id
  HAVING MAX(snapshot_at) >= strftime('%Y-%m-%dT%H:%M:%fZ','now','-3 days')),
live AS (
  SELECT DISTINCT ml.untappd_beer_id AS beer_id FROM taps t
  JOIN tap_snapshots ts ON ts.id = t.snapshot_id
  JOIN latest l ON l.pub_id = ts.pub_id AND l.s = ts.snapshot_at
  JOIN match_links ml ON ml.ontap_ref = t.beer_ref)
SELECT ef.issue_number AS issue, COUNT(*) AS rows_total,
  SUM(ef.beer_id IN (SELECT beer_id FROM live)) AS on_tap_now,
  SUM(ef.source_url <> '' AND ef.last_at >=
      strftime('%Y-%m-%dT%H:%M:%fZ','now','-14 days')) AS shop_seen_14d
FROM enrich_failures ef WHERE ef.issue_number IS NOT NULL
GROUP BY 1 ORDER BY on_tap_now DESC, shop_seen_14d DESC;"
```

- `on_tap_now` — сироти, що зараз на крані в пабі зі свіжим знімком
  (≤ 3 доби). Сильний сигнал.
- `shop_seen_14d` — рядки з крамниць, яких торкалося збагачення за 14 днів.
  **Слабкий** сигнал: живої таблиці асортименту крамниць немає, а `last_at`
  рухає й крон, не лише користувач. Він може лише підняти `Severity-4` до
  `Severity-3`, не вище.
- Issue, якого немає у виводі, не має жодного рядка: це кандидат на
  закриття, а не на severity.

Для хибних лінків (`Severity-2`) охоплення — кількість живих лінків, названих
в issue; перевір, що вони ще існують (`match_links`).

## Процедура розмітки

1. Читай **тіло й усі коментарі** issue: висновки й уточнення часто в
   коментарях, а заголовок описує симптом, не причину.
2. Визнач рівень за шкалою, потім застосуй модифікатори по порядку.
3. Одне речення обґрунтування, що називає **факт**: число з запиту, живий
   лінк, назву поломки. «Здається важливим» — не обґрунтування.
4. Якщо issue виглядає вже зробленим (згадано змерджений PR, 0 рядків,
   «done» у коментарях) — **не став severity**, а запиши як кандидата на
   закриття. Закриває людина.
5. Не сумнівайся на користь вищого рівня: коли два рівні однаково
   обґрунтовані, став нижчий і познач `?` в обґрунтуванні.
6. Інші лейбли не чіпай.

## Нові issues

Кожне нове issue отримує severity і effort при створенні або на
найближчому тижневому розборі. Сирітські issues, що бот створює
автоматично, приходять без них — їх розмічають за цим же документом.
