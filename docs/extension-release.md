# Випуск нової версії розширення (для maintainer)

Єдиний канал дистрибуції — **Chrome Web Store**. Off-store канал (zip через бота,
запис релізу в прод-БД, привілейований applier) **ретайрнуто** в #267.

## Реліз у стор (#266)

```bash
npm run release:store                 # package:store → upload → submit for review
npm run release:store -- --dry-run    # лише креденшели + preflight, нічого не мутує
```

Спершу:

0. **Змерджи реліз-PR у `main` — до запуску скрипта, а не після.** Google може
   опублікувати версію менш ніж за годину (0.16.0 — за 50 хвилин), а щойно вона
   стає live, найближчий тік #379 розсилає власникам токенів **посилання на
   чейнджлог**. Ту сторінку `scripts/render-docs.ts` будує **з `main`**, тож
   сабміт до мерджу означає розсилку, яка веде на сторінку без цієї версії.
   Саме так і сталося на 0.16.0: анонс пішов за 22 хвилини **до** мерджу, і
   четверо людей отримали посилання на чейнджлог, найновіший запис у якому був
   0.15.0. Міркування «пакет побайтово однаковий, змерджено чи ні» правдиве про
   **пакет** і хибне про **анонс**.

1. Підніми версію в `extension/package.json` — preflight відмовиться перезаливати
   версію, яку чернетка в сторі вже несе.
2. Перейменуй `## [Unreleased]` на `## [x.y.z] - DATE` у `extension/CHANGELOG.md`
   і **перечитай накопичені рядки очима користувача** — чейнджлог тепер не лише
   сторінка на Pages, а й увесь вміст анонсу (#379). Рядок, який не називає
   жодної видимої зміни («upgraded the test environment to jsdom 30»,
   «made card discovery independent of selector scoping»), **видаляється**, а не
   переписується; решта говорить мовою інтерфейсу, а не коду. Правила — у шапці
   самого `CHANGELOG.md`. Для **релізу** секція обов'язкова:
   `scripts/publish-store-release.ts` вимагає збігу, а `scripts/render-docs.ts` публікує
   цей файл як користувацький чейнджлог на GitHub Pages. (Дебажної збірки це не
   стосується — див. нижче.)
3. **Якщо реліз змінює те, що бачить рецензент — онови текст у дашборді ДО запуску
   скрипта.** Це опис крамниці й обґрунтування дозволів із `docs/cws-listing.md`
   (+ `docs/cws-review-notes.md`): новий магазин, новий дозвіл, нова опція. Порядок не
   косметичний — **щойно пакет відправлено на рев'ю, усі поля лістингу стають сірими й
   редагувати їх не можна до кінця рев'ю**, тож «заллю зараз, текст вставлю потім» не
   працює: версія їде в стор зі старим описом. Правильний порядок:

   1. вставити опис і обґрунтування host-дозволів у дашборді (айтем не в рев'ю — поля
      активні), зберегти чернетку;
   2. тоді `npm run release:store` — сабміт відправляє пакет **і** збережений текст разом.

   Якщо проґавив і версія вже опублікована: поля знову активні після завершення рев'ю —
   встав текст і надішли ще раз (рев'ю самого лістингу, без нової версії).

   ⛔ **Опис — не місце для переліку магазинів.** Такий сабміт Google уже відхилив
   2026-08-30 як keyword stuffing; чинний текст і пояснення — у `docs/cws-listing.md`.
   Відхилення лістингу не чіпає вже опубліковану версію розширення, але поля знову
   блокуються до кінця повторного рев'ю.

Store-збірка пишеться в **окремий** файл `warsaw-beer-overlay-<version>-store.zip` — вона
не той самий артефакт, що dev-zip (без `key`, вужчі дозволи), і не має його затирати.

### Одноразовий OAuth-сетап

1. Проєкт у Google Cloud → увімкнути **Chrome Web Store API**.
2. OAuth consent screen → **External**, далі **Publish app**, щоб статус став
   **In production**. У режимі *Testing* Google видає refresh-токени з життям 7 днів —
   автоматизація тихо помре між релізами.
3. Credentials → OAuth client ID → тип **Desktop app** → client id/secret у `.env` як
   `CWS_CLIENT_ID` / `CWS_CLIENT_SECRET`.
4. `npm run cws:auth` → відкрий URL (він же у `./tmp/cws-auth-url.txt`), дай доступ, тоді
   перенеси рядок `CWS_REFRESH_TOKEN=…` з `./tmp/cws-env.txt` у `.env`. Якщо браузер не
   дістає до `http://127.0.0.1:8976` (напр. він на іншій машині), візьми значення `code=`
   з адресного рядка: `npm run cws:auth -- --code <значення>`.
5. `npm run cws:auth -- --verify` має надрукувати рядок `OK — item …`.

Пізніший `invalid_grant` означає або відкликаний доступ, або consent screen, що з'їхав
назад у *Testing* — повтори крок 4.

## Дебажна збірка (лише для мейнтейнера)

`cd extension && npm run build` — хук `postbuild` кладе
`extension/warsaw-beer-overlay-<version>.zip`. Скачай цей один архів із сервера,
розпакуй локально й постав через chrome://extensions → Load unpacked.
Секція в `CHANGELOG.md` більше не потрібна, тож неопубліковані версії теж збираються.
