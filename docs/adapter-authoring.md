# Як додати адаптер нового магазину

Адаптер — це опис, як розпарсити сітку товарів конкретного магазину й де
накладати бейджі. Re-render при навігації працює **автоматично** для будь-якого
магазину — окремо вмикати його не треба.

> Ментальна модель: будь-який магазин з AJAX-навігацією (Shopify, Nuxt тощо)
> потребує re-render незалежно від того, SSR початковий рендер чи ні.
> **SSR ≠ «спостерігач не потрібен».**

## Кроки

1. **Зняти фікстуру сторінки колекції** → `extension/tests/fixtures/<id>.html`,
   де `<id>` — короткий стабільний ідентифікатор магазину.
   - SSR-магазин: `curl -A 'Mozilla/5.0' '<url колекції>' > extension/tests/fixtures/<id>.html`
   - SPA-магазин: дамп після рендеру через headless-Playwright — `npm run capture --
     <name> --parse` (`extension/scripts/capture-fixture.ts`), конфіг цілей —
     `extension/scripts/capture-targets.ts`.

2. **Реалізувати `SiteAdapter`** у `extension/src/sites/<id>.ts`:
   - обов'язкові: `id` (= ім'я фікстури), `hostMatch(url)`, `parseCards(root)`;
   - опційний `waitForGrid(root)` — лише для SPA, де сітка домальовується;
   - опційний `reRenderContainerSelector` — **тільки** звуження скоупу re-parse
     на шумних сторінках. Він НЕ вмикає re-render. Лиши порожнім, якщо сумніваєшся.

3. **Зареєструвати** адаптер у `extension/src/sites/registry.ts` (масив `ADAPTERS`).

4. **Додати домен нового магазину до manifest.** Онови `content_scripts[].matches`
   у `extension/manifest.config.ts` — інакше content script туди не інжектиться.
   Патерн дзеркалить `hostMatch`, напр.:

   ```ts
   'https://<host>/*',
   'https://*.<host>/*',
   ```

5. **Оновити каталог магазинів і всі користувацькі поверхні (обовʼязково).**
   - Додай один логічний магазин до `extension/src/popup/supported-shops.ts`,
     вкажи країну відправлення й підтримувані мовні адреси. Якщо адрес кілька,
     магазин у popup все одно має бути один; лічильник обчислюється автоматично.
   - Додай магазин, згрупований за країною відправлення, до `site/index.html`,
     `docs/extension-install-en.md` і `docs/extension-install-uk.md`. Перевір також
     quick start / розділ використання, щоб ніде не лишився застарілий набір.
   - Перезніми згорнутий і розгорнутий popup та заміни
     `site/assets/popup-supported-shops-collapsed.png` і
     `site/assets/popup-supported-shops-expanded.png`, щоб скріншоти показували
     актуальний лічильник і список. PR нового магазину без цих оновлень неповний.
   - **А от в опис у Chrome Web Store магазин НЕ додається.** Google відхилив сабміт
     2026-08-30 («Спам і розміщення в магазині», Yellow Argon) саме за перелік назв
     магазинів в описі — деталі й чинний текст у `docs/cws-listing.md`. Публічний опис
     відсилає до списку в popup'і; перелік доменів лишається тільки в обґрунтуванні
     host-дозволів, яке бачить лише рецензент.

6. **Прогнати конформанс-тест:** `cd extension && npm test -- src/sites/conformance.test.ts`.
   Він автоматично перевіряє парс, валідність селектора і **re-render після
   заміни сітки**. Червоний через відсутню фікстуру = нагадування зробити крок 1.

7. **Фільтр не-пива (обовʼязково).** Адаптер має класифікувати паки/сети/мерч/софт-дрінки
   як не-пиво або запобігати їхньому потраплянню до matching. Засоби: `isNonBeerName` з
   `src/sites/non-beer.ts` (пакувальні фрази/сертифікати);
   шоп-локальні токени в самому адаптері (як `MERCH_RE` в onemorebeer для скла/кухлів/мерчу);
   або опційний `isNonBeerPage(url)` для цілих не-пивних категорій (як onemorebeer `/delikatesy`).
   Для позитивно визначеного окремого товару поверни
   `{ el, brewery: '', name: '', nonBeer: true, skip: true }`; overlay поставить
   неклікабельний червоний `✕` і не надішле товар до API. Не використовуй цей стан для
   відсутньої назви, невдалого parse або network failure. `isNonBeerPage(url)` лишається
   для категорій, де вся сторінка гарантовано не-пивна; такі сторінки overlay не змінює.
   Позитивний per-card класифікатор не означає `continue` або `[]`: поверни підтверджену
   картку, описану вище.
   `<id>.nonbeer.html` зазвичай МУСИТЬ розпарситися в одну або більше підтверджених
   карток. FP-гарди (реальне пиво серед мерчу) і `isNonBeerPage` — у bespoke-тесті.
   Навмисний виняток — Beershop: category-fixture може вправляти whole-page gate; для
   кожної фікстури, що вправляє такий gate, bespoke-тест МУСИТЬ містити focused або
   synthetic mixed-grid proof для пива і не-пива.
   Якщо магазин підтверджено без не-пива — `tests/fixtures/<id>.nonbeer.json`
   `{ "none": true, "reason": "…" }` (причина обовʼязкова).

8. **Додати bespoke-тест** `extension/src/sites/<id>.test.ts` тільки на квірки
   магазину (одиниці виміру, формат назв тощо). Загальний контракт уже покрито
   конформансом — не дублюй його.

9. **Перевірити в реальному браузері** на 1–2 сторінках магазину: бейджі
   з'являються при першому завантаженні і **лишаються після пагінації/фільтра**.
