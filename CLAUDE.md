# Project: Warsaw Beer Crawler Bot
- **Stack**: Node.js, TypeScript, Telegraf (Telegram API), SQLite (база даних).
- **Style**: Функціональне програмування, модульна структура. Усі ключі доступу (API) мають читатися з файлу `.env`.
- **Workflow**: Використовуй автономний цикл (brainstorming -> writing-plans -> worktrees).
- **Повний цикл обов'язковий (override для skill `brainstorming`)**: skill `superpowers:brainstorming` (від 6.3.0) класифікує запит як spike / bounded / architectural і для `bounded` пропускає spec- і plan-документи. **У цьому проєкті шлях `bounded` не застосовується**: будь-яка зміна поведінки коду, що потрапляє в мердж, іде повним циклом architectural — spec у `docs/superpowers/specs/`, план у `docs/superpowers/plans/`, потім worktree. Незалежно від того, наскільки дрібною виглядає зміна. Причина: ця історія проєктування — робочий інструмент (ми повертаємось до неї при триажі орфанів і при розборі того, чому фікс не спрацював), тож дірка в ній коштує дорожче, ніж зайвий документ. Виняток — `spike`: суто дослідницька перевірка, яка **не залишає закомміченого коду** (напр. live-реплей прикладів з issue перед імплементацією, вимірювання стану прод-БД, перевірка зовнішнього API). Spike легітимний і документів не потребує, але його висновок веде назад у повний цикл, якщо з нього народжується зміна.
- **Design/plan-документи (місячні підтеки)**: історія проєктування живе у `docs/superpowers/specs/<YYYY-MM>/` та `docs/superpowers/plans/<YYYY-MM>/` — по місячних підтеках (напр. `specs/2026-07/2026-07-12-<topic>-design.md`, `plans/2026-07/2026-07-12-<topic>.md`). Нові документи клади у підтеку **поточного місяця**; найновіший документ — це останній файл у найновішій місячній теці. Верхній рівень `specs/`/`plans/` містить лише місячні теки (щоб не гортати пласку теку на 100+ файлів).
- **Testing**: Кожен новий модуль логіки має бути покритий базовими тестами (Vitest) перед злиттям гілки.
- **Spec**: `spec.md` (корінь репо) — єдине джерело істини за стандартом OpenSpec. Будь-яка імплементація має переглядатися на те, чи потрібно вносити зміни в спеку; якщо так — оновлювати `spec.md` у тому ж PR.
- **Extension docs**: будь-яка зміна, що зачіпає браузерне розширення (`extension/**`) і впливає на користувача — нова підтримувана крамниця, опція/чекбокс, popup-кнопка, нові бейджі/поведінка, потік встановлення/оновлення — **зобов'язана оновити інструкцію `docs/extension-install-uk.md` у тому ж PR** (як і `spec.md`). Перевіряй це наприкінці кожного extension-PR.
- **Чейнджлог розширення — користувацький текст, не технічний**: `extension/CHANGELOG.md` рендериться на GitHub Pages **і є всім вмістом анонсу релізу, який бот розсилає власникам токенів** (#379). Тому кожен рядок пишеться для того, хто користується розширенням: називай симптом, який людина бачила (бейдж не з'являвся, кнопка не працювала, пиво було під чужою броварнею), і що тепер, — термінами інтерфейсу, а не коду (жодних селекторів, адаптерів, обзерверів, service worker'ів, стадій парсингу). **Зміна, якої користувач не може помітити — тестова інфраструктура, бамп залежності, рефакторинг — у чейнджлог не потрапляє взагалі: рядок видаляється, а не перекладається людською мовою.** Це правило порушувалося непомітно, бо кожен PR додає свій рядок окремо, а перечитує їх лише реліз-зріз; повні правила — у шапці самого `CHANGELOG.md`, чекліст зрізу — крок 2 у `docs/extension-release.md`.
- **Декомпозиція `orphan-triage` issue → перемапити рядки**: issue з лейблом `orphan-triage` володіє набором рядків у прод-БД — `enrich_failures.issue_number` зв'язує кожну затріажену сироту з issue, чий фікс її врятує, і закриття цього issue бот читає як «фікс приїхав» (розмикає замок, дизайн: `docs/superpowers/specs/2026-08/2026-08-15-421-fix-keyed-lock-design.md`). Тому, **розбиваючи `orphan-triage` issue на під-issue або замінюючи його вужчим, перемапи його рядки в тому ж кроці**: `sudo -u warsaw-beer-bot bash -lc "sqlite3 /var/lib/warsaw-beer-bot/bot.db \"UPDATE enrich_failures SET issue_number = <під> WHERE beer_id IN (<ids>)\""`. Переносити тільки ті рядки, які під-issue справді покриває, і **ніколи** гуртом `WHERE issue_number = <батько>` на одну дитину: рядок, для якого не можеш назвати під-issue, лишається на батькові й платить свій один лукап, бо хибний лінк гірший за відсутній — він розімкнеться на закриття чужого issue. `review_class` при перемапуванні не чіпати: клас каже, який це дефект, номер issue — хто його фіксить; зміна обох разом позбавляє вердикт свідчення.
- **Фікс `parser_bug`/`matcher_bug` ухвалює долю КОЖНОГО свого рядка**: реплей перед фіксом обов'язковий і так, тож його вивід має лягти в БД, а не померти з сесією. Кожен рядок issue виходить із фіксу в одному з трьох станів — врятований (крон його злінкує), позначений `unrescued_at` (жива проба нічого не знайшла: закриття issue більше не дасть йому безкоштовного обнулення бекофу), або лишається в пулі без маркера. **По рядку, ніколи гуртом** `WHERE issue_number = …`. Маркер **не запечатує**: рядок лишається в пулі зі своїм бекофом, а будь-який явний ре-арм його чистить. `transient`/`blocked` — не вердикт, на них не позначають нічого. Інструмент: `adjudicateIssueRows` (`src/jobs/`, поруч із `unlock-fixed-orphans.ts`/`enrich-orphans.ts` — це джоба, а не ops-скрипт: DI-залежності, юніт-тести, живе там, де решта джоб).
- **Тека `./tmp/` (scratch)**: спільна тимчасова тека для поточної задачі. Користувач має проблеми з копіюванням із термінала, тож **коли потрібно, щоб користувач сам виконав shell-команду — НЕ друкуй її для копіювання, а поклади у файл під `./tmp/`** (напр. `./tmp/run.sh`) і дай шлях. Користувач також кладе туди файли для аналізу (HTML-захвати, дампи тощо). Тека **ефемерна й не комітиться** (у `.gitignore`): очищай **увесь** її вміст, коли поточну задачу завершено.
